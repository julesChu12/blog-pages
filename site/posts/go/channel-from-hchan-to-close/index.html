从 hchan 到 close：重新理解 Go Channel

2026 年 11 月 23 日
|

复习并发时，我能写出 ch := make(chan int)，也能用 range 读完一个关闭的 channel；但被问到“发送者到底阻塞在哪”“close 唤醒了谁”“select 怎么在多个就绪分支里选”时，还是需要翻源码确认。

本文从一次并发查询下游服务的场景出发，沿着 Go 1.25.8 的运行时实现，把 Channel 的收发、阻塞、关闭和 select 串起来。语言语义以 Go 规范和官方文档为准；涉及 hchan、sudog、gopark 和 selectgo 的部分，以 Go 1.25.8、macOS arm64 为观察基线，实现细节会随版本变化。配套例子位于 examples/go/concurrency/ 下的 channel-* 和 select-*，也同步在公开仓库 blog-code 的 go/concurrency 目录。

文中的配套例子如下，也保存在公开仓库 blog-code 的 go/concurrency/channel-fanout-query/main.go。读者可以把代码保存为 main.go 后直接运行：

package main

import (
	"fmt"
	"sync"
	"time"
)

type result struct {
	service string
	value   string
	err     error
}

// query 模拟一次下游查询：latency 内返回成功，否则在 timeout 后放弃。
func query(service string, latency, timeout time.Duration) result {
	select {
	case <-time.After(latency):
		return result{service: service, value: service + " 查询成功"}
	case <-time.After(timeout):
		return result{service: service, err: fmt.Errorf("超过 %s", timeout)}
	}
}

func main() {
	downstreams := []struct {
		name    string
		latency time.Duration
	}{
		{"user", 20 * time.Millisecond},
		{"stock", 200 * time.Millisecond}, // 慢下游
		{"coupon", 40 * time.Millisecond},
	}

	results := make(chan result)
	var wg sync.WaitGroup
	start := time.Now()

	for _, d := range downstreams {
		wg.Go(func() {
			results <- query(d.name, d.latency, 80*time.Millisecond)
		})
	}

	// 所有发送者结束后关闭 results，range 才能正常退出。
	go func() {
		wg.Wait()
		close(results)
	}()

	for r := range results {
		elapsed := time.Since(start).Round(10 * time.Millisecond)
		if r.err != nil {
			fmt.Printf("%-6s %-6s %v\n", elapsed, r.service, r.err)
			continue
		}
		fmt.Printf("%-6s %-6s %s\n", elapsed, r.service, r.value)
	}
	fmt.Println("全部下游结束")
}
go run "main.go"

本机运行结果：

20ms   user   user 查询成功
40ms   coupon coupon 查询成功
80ms   stock  超过 80ms
全部下游结束

这段输出对应四个环节：

  • 每个下游一个 goroutine，结果都发往同一个 results channel。
  • select 同时等待查询完成和 80ms 超时；慢下游到点后放弃，不影响其他分支。
  • 单独一个 goroutine 在所有发送者结束后 close(results)，range 才能正常退出。
  • 结果按完成顺序到达，而不是按启动顺序；channel 传递的是完成事件，不是固定顺序。

Channel 是什么：一个队列加两个等待队列

从运行时看，channel 是一个 hchan 结构：

type hchan struct {
	qcount   uint           // 当前队列中的元素数量
	dataqsiz uint           // 环形队列容量
	buf      unsafe.Pointer // 指向 dataqsiz 个元素的缓冲区
	elemsize uint16
	closed   uint32
	elemtype *_type
	sendx    uint // 发送索引
	recvx    uint // 接收索引
	recvq    waitq // 等待接收的 goroutine 队列
	sendq    waitq // 等待发送的 goroutine 队列
	lock     mutex
}

waitq 是 sudog 组成的双向链表；sudog 记录被阻塞的 goroutine、数据地址和唤醒结果。可以把它理解成“阻塞中的一次操作”，而不是 goroutine 本身。

字段分三类：

  • 数据：buf、dataqsiz、sendx、recvx、qcount 组成环形队列。
  • 状态：closed 标记是否已关闭；elemsize、elemtype 描述元素。
  • 同步：lock 保护所有字段；recvq、sendq 保存等待中的收发者。

make(chan T, n) 在编译器和运行时里会做尺寸检查，然后按元素类型选择分配方式：

switch {
case mem == 0:
	// 容量为 0 或元素大小为 0：只分配 hchan
	c = (*hchan)(mallocgc(hchanSize, nil, true))
case !elem.Pointers():
	// 元素不含指针：hchan 和 buf 放在同一块内存里
	c = (*hchan)(mallocgc(hchanSize+mem, nil, true))
	c.buf = add(unsafe.Pointer(c), hchanSize)
default:
	// 元素含指针：buf 单独分配，便于 GC 扫描
	c = new(hchan)
	c.buf = mallocgc(mem, elem, true)
}

所以“缓冲区”不一定是一次独立分配：元素不含指针时，它紧跟在 hchan 后面。无缓冲 channel 的 dataqsiz 为 0，buf 不承载数据。

当前版本的 hchan 还有 timer、bubble 等字段，服务于定时器 channel 和 synctest 实验；普通 channel 的语义不依赖它们，本文不展开。

无缓冲与有缓冲：阻塞点不同

无缓冲 channel 把发送和接收配成一次直接交接：

ch := make(chan int)
go func() { ch <- 42 }()
fmt.Println(<-ch) // 42

发送者先到时，会在 sendq 上阻塞；接收者到来后，运行时的 send/sendDirect 直接把值复制到接收者的栈上，然后唤醒发送者。反过来，接收者先到时在 recvq 上阻塞，发送者把值交给它。双方不需要缓冲区，也不需要把值先放进 buf。

有缓冲 channel 多了一个队列：

ch := make(chan int, 2)
ch <- 1
ch <- 2
fmt.Println(<-ch) // 1

sendx 指向下一个写入位置，recvx 指向下一个读取位置，qcount 记录当前元素数。写入后 sendx 前进，读完后 recvx 前进，越界就回到 0，形成环形队列。队列满时发送者阻塞，队列空时接收者阻塞。

两种 channel 的关键区别是：无缓冲 channel 的“就绪”依赖对端，只有一个等待队列非空时才可能完成；有缓冲 channel 在 qcount < dataqsiz 或 qcount > 0 时可以独立完成。 runtime/chan.go 开头的不变量也说明了这一点：通常 sendq 和 recvq 至少有一个为空。

发送：先走快路径，再挂起

chansend 的流程可以分成四段：

func chansend(c *hchan, ep unsafe.Pointer, block bool, callerpc uintptr) bool {
	if !block && c.closed == 0 && full(c) {
		return false // 非阻塞发送，队列满且未关闭
	}
	lock(&c.lock)
	if c.closed != 0 {
		unlock(&c.lock)
		panic(plainError("send on closed channel"))
	}
	if sg := c.recvq.dequeue(); sg != nil {
		send(c, sg, ep, func() { unlock(&c.lock) }, 3)
		return true // 有等待的接收者，直接交接
	}
	if c.qcount < c.dataqsiz {
		// 写入环形队列，返回
	}
	if !block {
		unlock(&c.lock)
		return false
	}
	// 构造 sudog，挂到 sendq，gopark
}

几个容易忽略的点：

  • nil channel 会永久阻塞。chansend 开头对 c == nil 直接 gopark，没有 goroutine 能唤醒它；这是“禁用分支”的基础。
  • 阻塞前会释放 channel 锁。gopark 通过 chanparkcommit 把锁交给调度器释放，否则接收者永远拿不到锁。
  • 被唤醒后要重新检查结果。发送者恢复后看 mysg.success：true 表示值已被接收；false 且 channel 已关闭，就 panic send on closed channel。
  • 无缓冲发送不经过 buf。即使有等待的接收者，也是直接复制；有缓冲时才会先写队列。

值从发送者到接收者，构成一次 happens-before：发送完成先于对应接收完成。Go 内存模型把它作为同步点，所以不需要额外的锁来发布数据。

接收：先读队列，再回应关闭

接收路径和发送对称，但关闭状态要单独处理：

lock(&c.lock)

if c.closed != 0 {
	if c.qcount == 0 {
		// 已关闭且缓冲区为空：零值 + false
		return true, false
	}
	// 已关闭但缓冲区还有数据：继续读队列
} else if sg := c.sendq.dequeue(); sg != nil {
	// 有等待的发送者：直接取它的值
	recv(c, sg, ep, func() { unlock(&c.lock) }, 3)
	return true, true
}

if c.qcount > 0 {
	// 从环形队列读取
	return true, true
}

这解释了两个常见行为：

  • 有缓冲 channel 关闭后不会清空缓冲区。前几次接收仍然拿到真实数据，ok 为 true；读空之后才返回零值和 false。
  • range 读到关闭且为空时结束。它每轮都在等“有数据”或“已关闭”；两者都满足时才退出，不会把缓冲区里的数据丢掉。

v, ok := <-ch 的 ok 只表示“这次接收是否来自尚未关闭的 channel”。单值接收 v := <-ch 丢掉 ok 后，无法区分“值恰好是零值”和“channel 已关闭”。

close：广播，而不是清空

closechan 的核心步骤：

// 简化版：省略了 race 检测、releasetime 和最后的 goready 循环
if c == nil {
	panic(plainError("close of nil channel"))
}
lock(&c.lock)
if c.closed != 0 {
	panic(plainError("close of closed channel"))
}
c.closed = 1

// 唤醒所有等待的接收者，让它们拿到零值、ok=false
for sg := c.recvq.dequeue(); sg != nil; sg = c.recvq.dequeue() {
	if sg.elem != nil {
		typedmemclr(c.elemtype, sg.elem)
		sg.elem = nil
	}
	sg.success = false
	glist.push(sg.g)
}

// 唤醒所有等待的发送者，它们恢复后会 panic
for sg := c.sendq.dequeue(); sg != nil; sg = c.sendq.dequeue() {
	sg.elem = nil
	sg.success = false
	glist.push(sg.g)
}
unlock(&c.lock)
// 释放锁之后再 goready，避免持锁唤醒

几个结论：

  • close 是广播。一次关闭会唤醒 recvq 上的所有接收者，而不是像发送那样只配对给一个接收者。context.Done() 正是利用这一点：cancel() 关闭 done channel，所有监听者同时解除阻塞。
  • close 不清空缓冲区。数据仍在 buf 里，按顺序读出；这也是“关闭后仍可接收”的原因。
  • close 只允许一次。重复 close 会 panic；工程上通常约定只由发送方关闭，或者用 sync.Once 包一层。
  • 关闭后发送会 panic，接收则永远立即返回零值和 false。

examples/go/concurrency/channel-close/main.go 把这几条放在一次运行里验证：

receive #1: value=1 ok=true
receive #2: value=2 ok=true
receive #3: value=3 ok=true
receive #4: value=0 ok=false
range: 10
range: 20
close nil channel        panic: close of nil channel
close closed channel     panic: close of closed channel
send on closed channel   panic: send on closed channel
blocked sender           panic: send on closed channel

有缓冲的 3 个元素在关闭后仍按顺序读出，第 4 次才返回零值和 false，range 正常结束；重复 close、close nil、向已关闭 channel 发送都会 panic。最后一行对应“阻塞中的发送者被唤醒后才 panic”，而不是 close 当场 panic。

close 不能用来“通知某个 worker 停下并强制它退出”。它只改变 channel 状态、唤醒等待者；worker 是否退出，取决于它有没有检查这个信号，和 Context 的协作取消是同一个道理。

select：随机顺序、统一加锁、一次挂起

select 在编译期会做简化：没有 default 且只有一个 case 时，直接退化成普通的收发；有 default 时，block 参数为 false。多分支的通用路径是 runtime/select.go 的 selectgo。

它先准备两个顺序：

  • pollorder：用 cheaprandn 做伪随机打乱，决定检查就绪的顺序。多个分支同时就绪时，不会固定选第一个。
  • lockorder：按 channel 地址排序，决定加锁顺序。所有参与 select 的 channel 一次性锁住，避免两个 select 交叉加锁造成死锁。

c == nil 的 case 会被直接跳过，不进入这两个顺序，所以 nil channel 在 select 里永远不会就绪。

// pass 1：按 pollorder 找已经就绪的 case
for _, casei := range pollorder {
	// 接收：有等待的发送者、缓冲区有数据、或已关闭
	// 发送：未关闭、有等待的接收者、或缓冲区有空位
}
if !block {
	return -1 // 有 default，且没有就绪分支
}

// pass 2：在每个 channel 上挂一个 sudog，然后只挂起一次
gopark(...)

// pass 3：唤醒后，把自己从其他 channel 的等待队列里摘掉

流程里有三个关键点：

  1. 所有 channel 一次性加锁。这保证了 select 检查多个 case 时看到的是同一个瞬间的状态，也解释了为什么 select 的 case 数量多时开销会上升。
  2. 只挂起一次。goroutine 在多个 channel 上各登记一个 sudog，然后统一 gopark；任意一个 channel 完成操作，就把它唤醒，再由它清理其他登记。
  3. 关闭的 channel 在接收分支永远就绪。selectgo 的 rclose 路径直接返回零值和 false；发送分支遇到已关闭 channel 则走 sclose，panic。

select 的随机性来自 pollorder 的洗牌，而不是“轮询”。它保证的是“多个就绪分支机会大致均等”，不是严格的公平调度。

nil 与 closed：一对反义词

状态发送接收在 select 中典型用途
nil永久阻塞永久阻塞永远不就绪禁用某个分支
closedpanic零值 + false接收分支永远就绪广播退出信号

nil channel 的“禁用”特性在 fan-in 里很有用：一个上游关闭后，把对应变量设为 nil，select 就不再从它读取零值。否则已关闭的分支每轮都就绪，会污染结果并让循环空转。examples/go/concurrency/fan-in-nil-channel/main.go 演示了这个过程。

closed channel 的“永远就绪”则是信号语义：context.Done() 关闭后，所有 <-ctx.Done() 都会立即返回。这里不能把“永远就绪”当成 bug——它取决于你把 channel 当数据源还是当信号。

一个小陷阱：用 if v == "" { continue } 兜底已关闭的 channel，会同时丢掉合法的空字符串和关闭事件。正确做法是两值接收，或者直接把分支置 nil。

工程上的几个边界

  • 只由发送方关闭。接收方关闭会让仍在发送的 goroutine panic；多个发送者时，用 sync.Once 或单独的协调者。
  • 缓冲区不是背压的万能药。缓冲只能吸收瞬时抖动；持续生产快于消费时，队列仍会满，内存也不会因为 cap 变大而自动受控。
  • 不要用 len(ch) 做同步。它只是一个瞬时快照，读到的值下一秒就可能变化；判断“是否还有数据”要靠关闭信号或额外的协调。
  • 无缓冲发送最容易泄漏 goroutine。没有接收者时，发送者会永久阻塞；用 select 配合 ctx.Done() 或超时分支退出。
  • channel 适合传递所有权和事件，不适合保护共享状态。需要保护一组字段时，Mutex 往往更直接；这也是并发文章接下来要讨论的部分。
  • 不要依赖 goroutine 的唤醒顺序。close 唤醒所有等待者，但谁先运行由调度器决定；缓冲 channel 保证元素 FIFO，不保证 goroutine 执行顺序。
