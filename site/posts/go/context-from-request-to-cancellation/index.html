从请求到取消：重新理解 Go Context

更新于: 2026 年 11 月 23 日
|

日常写 Go 时，ctx context.Context 几乎出现在每个函数签名里，但真正需要判断的是：用户取消后，下游 RPC 会不会停？超时到底取消了谁？调用 cancel() 之后，子任务是不是已经退出？

一个下单请求可能并发检查钱包、库存和优惠券。如果用户取消请求，或者库存查询已经超时，我们希望无用的工作尽快结束。本文从这个场景出发，区分 Context 的接口契约与 Go 1.25.8 的实现。

分析以 Go 语言规范和官方文档为准；涉及 cancelCtx、timerCtx 和传播路径的部分，以 Go 1.25.8、macOS arm64 为实现基线，这些细节可能随版本和架构变化。文中涉及的资源下载和下单检查均为演示场景，可运行的配套例子位于 examples/go/concurrency/ 下的 context-lifecycle、context-timeout、context-http 和 context-cause。

文中的配套例子如下，也保存在源码仓库的 examples/go/concurrency/context-lifecycle/main.go。读者可以把代码保存为 main.go 后直接运行：

package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

func main() {
	parent, cancelParent := context.WithCancel(context.Background())
	defer cancelParent()

	wallet, cancelWallet := context.WithCancel(parent)
	defer cancelWallet()
	stock, cancelStock := context.WithCancel(parent)
	defer cancelStock()

	observed := make(chan struct{})
	allowCleanup := make(chan struct{})
	var wg sync.WaitGroup
	wg.Go(func() {
		<-wallet.Done()
		close(observed)
		<-allowCleanup // 模拟收到取消后仍需完成清理
		fmt.Println("钱包任务：清理完成")
	})

	cancelStock()
	fmt.Println("库存取消:", stock.Err())
	fmt.Println("父节点仍有效:", parent.Err() == nil)
	fmt.Println("钱包仍有效:", wallet.Err() == nil)

	cancelParent()
	<-observed
	fmt.Println("钱包任务：已观察到取消，清理尚未完成")
	close(allowCleanup)
	wg.Wait()
	fmt.Println("所有任务已结束")

	cause := errors.New("库存查询超时")
	timed, cancelTimed := context.WithTimeoutCause(context.Background(), 10*time.Millisecond, cause)
	defer cancelTimed()
	<-timed.Done()
	fmt.Println("超时状态:", timed.Err())
	fmt.Println("超时原因:", context.Cause(timed))
}
go run "main.go"

本机运行结果：

库存取消: context canceled
父节点仍有效: true
钱包仍有效: true
钱包任务：已观察到取消，清理尚未完成
钱包任务：清理完成
所有任务已结束
超时状态: context deadline exceeded
超时原因: 库存查询超时

这段输出对应三个结论：

  • 取消库存子节点，不影响父节点和钱包分支：取消是向下传播的。
  • 钱包任务已经观察到取消，但 wg.Wait() 仍要等它完成清理。取消信号和任务退出是两个事件。
  • WithTimeoutCause 到期后，Err() 是通用的 DeadlineExceeded，具体原因在 Cause() 里。

Context 传递什么

context.Context 是接口，包含四个方法：Deadline 返回截止时间，Done 返回取消通知通道，Err 返回通用取消状态，Value 读取请求级数据。Context 可以跨 goroutine 传递，任务仍需在阻塞点或长时间操作中响应取消。

context.Background() 通常用作独立任务的根；context.TODO() 用于暂时尚未确定合适 Context 的位置。二者本身没有截止时间和取消信号。请求处理链通常接收上游传入的 ctx，而不是在中间重新创建根节点。

func handleOrder(ctx context.Context, req OrderRequest) error {
	ctx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
	defer cancel()

	return checkOrder(ctx, req)
}

ctx 是函数的第一个参数，也是调用链上唯一的取消入口。把它存进结构体、或者用 context.Background() 覆盖上游传来的 Context，都会让取消信号在这里断掉。

下单请求的父子关系

orderCtx
├── walletCtx
├── stockCtx
│   └── stockRPCCtx
└── couponCtx

调用库存的 cancelStock() 会取消 stockCtx 和它的后代，钱包、优惠券和父节点仍可继续。取消 orderCtx 则向下通知所有后代。每个节点第一次生效的取消状态和原因会保留下来。

在 Go 1.25.8 中，WithCancel 创建 cancelCtx：

type cancelCtx struct {
	Context

	mu       sync.Mutex
	done     atomic.Value          // chan struct{}，第一次 cancel 时关闭
	children map[canceler]struct{} // 第一次 cancel 时置 nil
	err      atomic.Value          // 第一次 cancel 时写入
	cause    error
}

Done 的 channel 是懒创建的：没人调用 Done() 时，done 为 nil；第一次调用才在锁内 make(chan struct{})。children 保存可取消的子节点，err 和 cause 只写第一次。

子节点通过 propagateCancel 登记到父节点。源码按父节点的类型分了几条路：

  1. 父的 Done() 为 nil：父永远不会取消，直接返回。
  2. 父已经取消：立刻取消子节点，带着父的 Err 和 Cause。
  3. 父是 *cancelCtx 或派生自它：加锁，把子节点放进父的 children map。
  4. 父实现了 AfterFunc(func()) func() bool：用 AfterFunc 注册回调，并用 stopCtx 保存停止函数。
  5. 其他自定义 Context：起一个 goroutine 监听父的 Done，同时监听子的 Done 以便提前退出。

所以“父子关系”不是对象继承，而是子节点把自己登记到父节点的等待集合里。父取消时遍历这个集合，逐个调用子的 cancel。

取消信号和任务退出是两个事件

父 Context 取消后，任务可能正在清理，也可能卡在不支持取消的操作中。cancel() 发出信号，不会等待任务退出。需要确认结束时，使用 WaitGroup、errgroup.Wait() 或其他同步机制。

开头的例子用两个 channel 控制清理时序：observed 表示任务已经看到取消，allowCleanup 放行清理。所以输出里会先看到“已观察到取消”，再看到“清理完成”，最后才是 wg.Wait() 返回。示例中的同步通道用于明确事件顺序，并不依赖打印顺序猜测任务状态。

如果调用方可能提前离开，向无缓冲 channel 发送结果时也需要考虑取消：

select {
case resultCh <- result:
	return nil
case <-ctx.Done():
	return ctx.Err()
}

如果发送和取消同时可执行，select 可能选择任一分支。若业务要求取消后绝不产生某种副作用，还需要设计额外的同步或业务协议。

Done 关闭时，所有等待者同时被唤醒

Done() 返回的是一个只读 channel。取消发生时，cancelCtx.cancel 关闭它：

d, _ := c.done.Load().(chan struct{})
if d == nil {
	c.done.Store(closedchan) // 没人等过，复用包级已关闭 channel
} else {
	close(d)
}

closedchan 是包初始化时就关闭好的共享 channel。如果这个 Context 从创建到取消都没有人调用过 Done()，就不需要新分配一个 channel；之后有人再调用 Done()，拿到的 closedchan 立刻可读，语义完全一致。

关闭 channel 是广播：所有阻塞在 <-ctx.Done() 上的 goroutine 会在同一时刻被唤醒，而不是只唤醒一个。发送做不到这一点——发送是点对点的，而且没有接收者时会阻塞。context 只取消一次，也避免了重复关闭 channel 的 panic；cancelCtx.cancel 开头的 err 检查承担了类似 sync.Once 的角色。

Err() 还有一个时序保证：

if err := c.err.Load(); err != nil {
	<-c.Done() // 返回错误前，确保 Done 已经关闭
	return err.(error)
}
return nil

所以只要看到 ctx.Err() != nil，就可以确定 Done() 已经关闭。

cancel 的幂等与子节点清理

cancelCtx.cancel 做四件事：写入第一次的 err 和 cause、关闭或替换 done、递归取消所有子节点、按需把自己从父节点移除。

// 简化版：省略了 closedchan 复用、removeChild 和加锁后的细节
func (c *cancelCtx) cancel(removeFromParent bool, err, cause error) {
	c.mu.Lock()
	if c.err.Load() != nil {
		c.mu.Unlock()
		return // 已经取消过，后面全部忽略
	}
	c.err.Store(err)
	c.cause = cause
	// 关闭 done 或复用 closedchan
	for child := range c.children {
		child.cancel(false, err, cause) // 向下传播
	}
	c.children = nil // 释放对子节点的引用
	c.mu.Unlock()
}

三个细节值得记住：

  • 第一次取消生效。父先取消，子之后再调用自己的 cancel() 会被 err 检查挡掉。
  • children 在取消后置 nil。父节点不再通过自己的字段持有子节点，避免整条 Context 链被父节点一直引用。
  • 子节点提前取消时要 removeChild。否则父节点的 children map 会一直持有这个已经结束的子节点。取消动作本身是幂等的，不会重复通知，但引用会滞留；长生命周期的父 Context 配上大量短命子 Context 时，这是实打实的内存增长。

timerCtx 和 afterFuncCtx 都重写了 cancel：前者先停定时器，后者还要处理回调的启动或停止。

超时、截止时间和资源清理

WithTimeout(parent, d) 接收相对时长，WithDeadline(parent, t) 接收绝对时间。子节点的有效截止时间不会晚于父节点。父节点只剩 300 毫秒时，子节点再设置 500 毫秒的超时，仍会跟随父节点较早结束。

stockCtx, cancelStock := context.WithTimeout(orderCtx, 500*time.Millisecond)
defer cancelStock()

err := checkStock(stockCtx)

这个“跟随父节点”不是把时间复制过去，而是直接放弃创建定时器。WithDeadlineCause 开头有一段短路：

if cur, ok := parent.Deadline(); ok && cur.Before(d) {
	// 父节点更早，退化成普通 cancelCtx，不再创建 timerCtx
	return WithCancel(parent)
}

此时返回的 Context 只是一层 cancelCtx，Deadline() 沿嵌入的父 Context 返回 300ms；WithTimeout 传进来的 500ms 根本没有机会生效。截止时间已经过去时，则立即以 DeadlineExceeded 取消。

只有真正需要新截止时间时，才会创建 timerCtx：

type timerCtx struct {
	cancelCtx
	timer    *time.Timer // 受 cancelCtx.mu 保护
	deadline time.Time
}

定时器到期时调用 cancel；提前取消时，timerCtx.cancel 会 Stop() 并置 nil，然后委托给 cancelCtx.cancel。即使查询提前成功，也要调用 cancelStock()：

  • 停止可能还在运行的定时器
  • 把子节点从父节点的 children 里移除
  • 让 Done() 进入已关闭状态，避免下游继续等待

忘记调用会被 go vet 的 lostcancel 检查发现。Context 的信号不会自动清理任务持有的文件、响应体等资源，任务应自行释放。

Err、Cause 和取消原因

Err() 只返回两个标准值：

  • context.Canceled：被主动取消，或父节点取消
  • context.DeadlineExceeded：截止时间到达

更具体的原因放在 Cause() 里。WithCancelCause 允许取消时带一个 error，WithTimeoutCause 和 WithDeadlineCause 则在定时器到期时记录指定原因：

stockCtx, cancelStock := context.WithTimeoutCause(orderCtx, 500*time.Millisecond, ErrStockTimeout)
defer cancelStock()

if errors.Is(stockCtx.Err(), context.DeadlineExceeded) {
	// 粗粒度：是超时，不是用户取消
}
if errors.Is(context.Cause(stockCtx), ErrStockTimeout) {
	// 具体原因：库存查询超时
}

优先级只有一个规则：第一次取消生效，后到的全部忽略。

场景Err()Cause()
父先取消，带着 causeACanceledcauseA
子先超时，带着 causeBDeadlineExceededcauseB
父先取消，子之后才超时CanceledcauseA
子先超时，父之后才取消DeadlineExceededcauseB
没有显式 cause同 Err()同 Err()

有一点容易踩坑：WithTimeoutCause 只有定时器到期时才带 cause；手动调用它返回的 cancel()，Err() 是 Canceled，cause 为 nil，Cause() 会退化成返回 Canceled。

examples/go/concurrency/context-cause/main.go 用两种先后顺序验证了这张表：

父先取消: err=context canceled cause=parent-cancel
定时器后: err=context canceled cause=parent-cancel
子先超时: err=context deadline exceeded cause=child-timeout
父后取消: err=context deadline exceeded cause=child-timeout
父自身:   err=context canceled cause=parent-cancel

后两行还说明：子节点取消不会向上传播，父节点保持自己的状态。

RPC 取消和远端任务

对于支持 Context 的客户端，把请求 Context 继续传给客户端 API。HTTP 请求可以用 http.NewRequestWithContext(ctx, ...) 创建，http.Client.Do 和响应体读取受请求 Context 的生命周期约束。

客户端取消后，请求的 Context 关闭，传输层会中断连接并返回；服务端在连接关闭或请求结束时也会取消对应的请求 Context。但服务端 handler 是否停下，取决于它有没有检查这个 Context：不检查、或者不把 ctx 传给数据库和下游 RPC，业务代码会继续跑完。客户端超时也不能证明远端写操作没有成功，涉及重试时需要结合幂等和结果查询。

多个下载或查询任务可使用 errgroup.WithContext：

g, groupCtx := errgroup.WithContext(ctx)
g.Go(func() error { return checkWallet(groupCtx) })
g.Go(func() error { return checkStock(groupCtx) })
g.Go(func() error { return checkCoupon(groupCtx) })

if err := g.Wait(); err != nil {
	return fmt.Errorf("check order: %w", err)
}

第一个任务返回非 nil 错误后，任务组取消派生 Context，其他任务可以响应退出；Wait 等所有任务返回后给出第一个错误。如果某个任务一直不响应取消，Wait 仍会等待。任务组的派生 Context 在 Wait 返回时也会被取消，后续独立操作应使用合适的父 Context。

取消原因和后台工作

WithoutCancel(parent) 保留对父节点 Value 的读取，同时隔开父节点的取消和截止时间。它可以用于请求结束后仍要执行、允许丢失的后台工作；通常在后台 goroutine 内再次创建超时 Context，并由该 goroutine 调用 cancel。这不会让任务脱离进程，可靠任务需要持久化或其他可靠交付机制。

go func(ctx context.Context) {
	ctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)
	defer cancel()
	writeAuditLog(ctx, orderID)
}(ctx)

context.AfterFunc(ctx, f) 在 Context 取消时启动回调，返回的 stop 可以尝试阻止回调启动。stop 不等待已经开始的回调，也不取消 Context；要确认回调结束，需单独同步。Context 如果已经取消，回调会立即在新的 goroutine 中启动。

工程上的几个边界

  • 父 Context 传 nil 会直接 panic：context: cannot create context from nil parent。
  • 不要依赖 Context 的相等比较，也不要拷贝；把它作为参数传递，而不是存进配置或结构体字段。
  • WithValue 的值沿父链查找，只适合请求 ID 一类跨 API 的请求级信息，不要用来传可选参数。key 要可比较，推荐用自定义的非导出类型，避免和字符串 key 冲突；其中保存的可变对象仍需按对象自身的并发规则保护。
  • 自定义 Context 很少有必要；如果实现，必须遵守 Done 只关闭一次、Err 只在取消后返回非 nil 的契约。
  • cancel() 是释放资源的手段，不是等待任务结束的手段。需要“取消并收尾完成”时，先 cancel()，再 Wait()。
