从创建到扩容：重新理解 Go Slice

2026 年 11 月 10 日
|

复习 Go slice 时，我发现自己能写 make 和 append，但遇到几个切片共用数组时，仍然需要停下来判断：追加会不会改到原数据？容量不足时到底复制了什么？

要回答这些问题，需要沿着 slice 的生命周期，把切片值、底层数组和元素可能引用的对象分别看清楚。本文从创建切片开始，一直追踪到扩容后的复制与初始化。

语言语义以 Go 规范为准；涉及容量增长、存储位置和运行时调用的观察，基于 Go 1.25.8、macOS arm64。这些实现细节可能随着版本、架构和编译选项变化。

创建切片：先分清切片值和底层数组

s := []int{10, 20, 30}

切片值记录它引用的数组位置、长度和容量：

s：len=3、cap=3 ──→ 底层数组 [10 20 30]

可以把这个字面量在语义上理解为：先准备一个 [3]int 数组，再取得它的切片。s 是 []int，并不是 [3]int；对 s 赋值也不会自动复制数组中的所有元素。

len 决定当前可以直接索引的元素范围；cap 表示从切片起点开始，可以通过重新切片使用的底层数组范围。当前机器上 unsafe.Sizeof(s) 是 24 字节，不包含底层数组；数组中的三个 int 各占 8 字节，元素空间也是 24 字节。两者相同只是这个例子的巧合。

var a []int     // nil 切片：len=0，cap=0
b := []int{}    // 非 nil 空切片：len=0，cap=0
c := make([]int, 2, 5)

a 和 b 打印时都可能显示为 []，但 a == nil 为 true，b == nil 为 false。c 的长度为 2、容量为 5：前两个元素已经存在且可直接索引，值初始为 0；容量表示底层数组能够容纳 5 个元素。

make([]int, 2, 5) 所需的底层元素空间，在本机是 5 × 8 = 40 字节。如果实际走到堆分配，分配器的槽位可能更大，但切片的容量仍是 5。长度、容量以元素数计，分配器管理的槽位以字节计。

日常代码中，已知结果数量并准备按索引填充，可以使用 make([]T, n)；如果只知道数量上限、打算逐个追加，可以使用 make([]T, 0, n)。例如：

numbers := []int{1, 2, 3, 4}
even := make([]int, 0, len(numbers))

for _, n := range numbers {
	if n%2 == 0 {
		even = append(even, n)
	}
}
// even = [2 4]

如果这里写成 make([]int, len(numbers)) 再 append，前面已经存在的四个零值元素不会被覆盖，而会保留在结果中。

切片范围：结束位置不包含在内

base := []int{1, 2, 3, 4}
part := base[1:3] // [2 3]

base[1:3] 包含索引 1，不包含索引 3；长度为 3 - 1 = 2。这种左闭右开规则使相邻区间可以使用同一个边界，例如 base[:2] 和 base[2:] 正好分开，不重复也不遗漏。

起点省略时默认为 0：

a := base[:2]   // 等价于 base[0:2]；len=2，cap=4
b := base[:2:2] // len=2，cap=2

普通切片表达式 base[:2] 保留从起点开始的剩余容量；完整切片表达式 base[:2:2] 把容量限制为 2。限制容量不会立即复制数组，a、b 仍然引用 base 的底层数组。Go 规范对完整切片表达式的定义规定了 low:high:max 的长度和容量计算。

赋值、传参和 append：哪些数据共享？

先看容量足够的情况：

base := []int{1, 2, 3, 4}
a := base[:2]     // [1 2]，len=2，cap=4
b := append(a, 9) // 新长度为 3，仍未超过容量 4
b[0] = 100

fmt.Println(base) // [100 2 9 4]
fmt.Println(a)    // [100 2]
fmt.Println(b)    // [100 2 9]

append 复用原数组，将 9 写在索引 2，覆盖原来的 3。b[0] = 100 修改的是同一个数组，因此 base 和 a 也能看到。a 的长度仍是 2，所以它打印时不包含索引 2 的元素。

再把 a 的容量限制为 2：

base := []int{1, 2, 3, 4}
a := base[:2:2]   // [1 2]，len=2，cap=2
b := append(a, 9) // 需要长度 3，超过容量 2
b[0] = 100

fmt.Println(base) // [1 2 3 4]
fmt.Println(a)    // [1 2]
fmt.Println(b)    // [100 2 9]

这次 append 需要新的底层数组，先保留 a 的两个元素，再追加 9。因此对 b[0] 的修改不会改变 base 或 a。两组实验可以运行：

go run "examples/go/day01/slice-sharing/main.go"

切片赋值和函数传参同样需要区分切片值与数组。b := a 复制切片值；b = b[:1] 只改变 b 的长度，但通过 b[0] 修改共享数组，仍可能被 a[0] 看到。函数参数收到的也是切片值副本，因此函数内部执行 s = append(s, x) 后，如果调用者需要新的长度或数组，应返回新切片并让调用者接收。

新数组不一定带来独立对象：浅拷贝

数组元素是整数时，扩容复制整数值；如果元素是指针，复制的是指针值：

type Cell struct{ Value int }

cell := &Cell{Value: 1}
a := []*Cell{cell}
b := append(a[:1:1], &Cell{Value: 2})

b[0].Value = 100

fmt.Println(&a[0] == &b[0]) // false：数组槽位不同
fmt.Println(a[0] == b[0])   // true：指向同一个 Cell
fmt.Println(a[0].Value)     // 100

a 和 b 的底层数组分开了，但第一个元素仍保存相同的对象地址。b[0].Value = 100 修改的是共同指向的 Cell。如果要让对象也独立，需要根据数据结构继续复制指针指向的对象；对象内部还有切片、map 或指针时，也要明确哪些数据需要独立。

copy(dst, src) 同样复制元素值，并不会自动递归复制元素引用的对象。它复制的数量是 len(dst) 和 len(src) 中较小的值，而不是依据 cap(dst)：

src := []int{1, 2, 3}
dst := make([]int, 0, 3)

fmt.Println(copy(dst, src)) // 0：dst 的长度为 0

扩容策略：减少搬迁与预留空间的取舍

逐个追加元素时，如果每次都只增长到刚好够用，下一次追加又会触发增长。对 10,000 个元素，本地 slice-growth-design 示例得到：

策略逻辑增长次数旧长度累计值最终容量空余槽位
每次刚好够用的模型1000049995000100000
翻倍增长模型1516383163846384
约 1.25 倍增长模型384134410349349
Go 1.25.8 本机观察1932415122882288

前三行仅模拟逻辑容量；最后一行实际执行 Go append，并在容量变化时累计旧长度。表中不是耗时基准，也不能把逻辑增长次数直接等同于堆分配次数。把最终元素数换成其他值，空余容量的比较也可能不同。

这个实验说明了基本取舍：增长较大，通常可以减少增长和旧元素搬迁的频率，但可能保留更多暂时未用的空间；增长较小则可能更频繁地搬迁。实际运行开销还需要结合元素类型、分配、GC 和基准测试判断。

go run "examples/go/day01/slice-growth-design/main.go"

Go 1.25.8：候选容量和最终容量

在本机 Go 1.25.8 的 nextslicecap 中，概括普通增长路径：

  • 所需新长度超过旧容量两倍时，候选容量从所需新长度开始。
  • 旧容量小于 256 时，候选容量按两倍增长。
  • 旧容量达到 256 后，通过公式从约两倍逐渐向 1.25 倍过渡。

以 []int 旧容量为 512、追加一个元素为例：

新长度：513
候选容量：512 + (512 + 3 × 256) / 4 = 832
候选字节数：832 × 8 = 6656
分配器尺寸取整：6656 → 6784 字节
最终容量：6784 ÷ 8 = 848 个 int

832 是增长公式的候选结果，848 是本机考虑分配器尺寸后的观察结果。Go 规范并不保证扩容倍率或最终容量数值；业务代码应依赖追加后的数据和容量足够使用，而不是写死某个扩容结果。源码中的 roundupsize 负责按分配器规格处理字节大小。

一次扩容：判断、复制、写入和清零

s := make([]int, 2, 2)
s[0], s[1] = 10, 20
old := s

s = append(s, 30)

追加后所需长度为 3，大于旧容量 2。在当前 Go 1.25.8 的普通编译路径中，编译器会生成“新长度与旧容量”的比较；对于需要运行时增长的路径，再调用 growslice。容量足够时则不必走这条增长路径。具体条件和栈缓冲优化可从 state.append 查看。

本机这次实验中新容量为 4。针对 []int，可以把新数组分为三段：

索引：          0    1    2    3
新数组：      [10   20 | 30 |  0]
               └──────┘ └──┘ └──┘
               旧元素    新增  剩余容量
  1. growslice 准备新空间，并通过 memmove 复制旧长度范围内的元素。
  2. 追加代码写入 30；growslice 的参数包含追加数量，但不包含这个具体的元素值。
  3. 对无指针元素的当前路径，剩余容量部分需要清零，因为之后可以通过重新切片访问；即将被追加代码覆盖的区域则不必在 growslice 中先清零再覆盖。

如果元素包含指针，运行时需要按指针类型处理初始化，并在写屏障启用时进行相应的批量屏障处理，避免 GC 漏掉需要追踪的引用。完整的标记和回收机制留到 GC 专题。

追加完成后：

old → 旧数组 [10 20]，len=2，cap=2
s   → 新数组 [10 20 30]，len=3，cap=4

扩容不会自动让旧数组立刻消失：只要 old 或其他可达引用仍需使用它，就必须保留。堆对象不再可达后才有资格被 GC 回收，回收时间不等于 append 执行时间。

编译器、运行时和内存分配的边界

字面量和 make 的类型、已知数量可以在编译时分析；实际存储方式则与生命周期、大小和编译优化有关。不能看到 make 就断言一定发生堆分配，也不能把“返回切片”单独作为所有情况下必然堆分配的规则。

在本机、保留 //go:noinline 函数边界的独立实验中，localSum 的 make([]int, 4) 报告为 does not escape，returnedSlice 的同一写法报告为 escapes to heap。复现：

go build -o "/tmp/slice-escape" -gcflags="-m=2" \
  "examples/go/day01/slice-escape/main.go"

编译结果还可用 -gcflags="-S" 查看。VS Code 的 Go 调试器也可以在断点暂停后打开反汇编视图；调试构建通常关闭部分优化，所以指令可能与普通构建不同。

当代码实际进入堆分配路径时，本机的字面量案例观察到 runtime.newobject，返回 make 的案例观察到 runtime.makeslice；两者在本版本中都可调用 mallocgc。小对象按尺寸类别寻找可用槽位，本地缓存不足时再向其他运行时管理层补充。不是每次 append 都会调用这些函数，也不是每次堆分配都会向操作系统申请新内存。

带走的判断方法

遇到一段 slice 代码时，先画出切片值和底层数组，再按顺序问：

  1. 每个切片的 len、cap 是多少？它们是否引用同一个数组？
  2. append 后所需长度是否超过容量？返回值赋给了谁？
  3. 如果数组分开，元素是否仍含指针或其他引用，导致对象继续共享？
  4. 性能问题是否有实际测量？容量和分配结论是否只适用于特定 Go 版本、架构与编译条件？

这些问题能先确定程序行为，再决定是否值得继续看编译器、运行时源码或性能数据。
