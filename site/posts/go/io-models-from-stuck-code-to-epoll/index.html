从阻塞读到 epoll：重新理解 Linux IO 模型

2026 年 11 月 26 日
|

平时用 Go 写网络服务时，很容易习惯性地在循环里写 conn.Read(buf)，觉得网络读取本来就该这么直白。直到重新梳理操作系统底层的 IO 模型，把多线程、非阻塞轮询、select、poll 和 epoll 顺着同一个问题串了一遍，才明白为什么早年的 C/Node.js 服务器写得那么别扭，以及 Go 运行时到底替业务代码接管了什么。

本文从一段单连接的阻塞读代码开始，沿每一种模型遇到的具体瓶颈往下推进，最后对照 Go netpoll 在本机上的实测数据收尾。

一段只有一个客户端时正常的阻塞代码

// 最直白的同步阻塞模型：一次只照顾一个连接
ln, _ := net.Listen("tcp", ":8080")
conn, _ := ln.Accept()      // 阻塞直到第一个客户端连上来
buf := make([]byte, 1024)
n, _ := conn.Read(buf)      // 阻塞等待数据；客户端不发包，线程就一直停在这
handle(buf[:n])             // 读到数据后再处理业务blocking-server.go

只有一个客户端时，这段代码线性、直白：Accept 等到连接，Read 等到数据，handle 处理请求。

问题出现在第二个客户端连上来的时候。假设第一个客户端建立连接后迟迟不发数据，单线程程序就会一直停在 conn.Read(buf) 这一行等待内核缓冲区就绪。就在这时，第二个客户端把数据发过来了，服务端却没有任何反应，因为唯一的线程被卡在第一个连接的阻塞读上，既不知道第二个连接已有数据，也抽不出手去读。

把整个问题的根源收成一句话，就是：Read 在等待数据时，调用线程什么都干不了。 这并不是某种语言的特性，而是操作系统“阻塞读”本身的性质。

解决思路：多线程与非阻塞读

想让服务端同时照顾多个连接，能想到的直接办法有两条。

第一条是多开线程。来一个连接就分配一个线程去盯，第一个线程卡在 conn1.Read 时，第二个线程照常去读 conn2，互相不耽误。这就是传统的多线程并发模型。

第二条是让 Read 不再干等。把套接字设成非阻塞模式，没有数据可读时 read() 立刻返回一个错误码，线程不去睡眠，而是转头去问下一个连接。这就是非阻塞 IO。

两条路都能在连接数很少时跑通，但往高并发场景一推，各自都会碰上硬瓶颈。

多线程的瓶颈：C10K 问题

10 个连接开 10 个线程完全可行，但连接数涨到一万时，线程的成本就会把机器拖垮：

  • 每个线程都有独立的内核栈和用户态栈，Linux 默认线程栈大小通常为 8MB（虚拟内存），一万个线程光栈空间就要占去几十 GB 虚拟地址空间。
  • 内核需要为每个线程维护调度实体和上下文，频繁在数千个线程间做上下文切换会吃掉大量 CPU。

当“连接数 = 线程数”时，单机能扛住的并发量很快就会触顶。这正是 Dan Kegel 在 1999 年总结的 C10K 问题：单台服务器如何同时处理一万个以上的并发连接。

非阻塞轮询的代价

改用非阻塞 IO（给 fd 设置 O_NONBLOCK）后，单个线程用一层循环就能扫过所有连接：

// 动机：用单个线程轮询所有非阻塞连接，省掉海量线程开销
for {
	for _, conn := range conns {
		// 无数据时立刻返回 EAGAIN，不再把线程挂起
		n := read(conn) 
		if n > 0 {
			handle(...)
		}
	}
}nonblocking-loop.go

线程数降到了 1 个，内存压力也没有了，但这个循环一直在用户态和内核态之间空转。一万个连接在绝大多数时刻都没有数据可读，而每调用一次 read 都是一次系统调用；一轮问下来一万次系统调用里可能九千九百多次都是无功而返，CPU 直接被无效轮询吃满。

如果为了省 CPU 在每轮之间加上 sleep(10ms)，响应延迟又会被拉高。用 CPU 空转去换低延迟，两头都不划算。

select 与 poll：把等待交给内核

既然用户态挨个发系统调用太贵，很自然的想法是把“我要盯哪些连接”一次性交给内核，由内核替程序等；只要其中任何一个连接就绪，内核再把进程唤醒。

1983 年 BSD 引入的 select 干的就是这件事：

// 动机：把等待交给内核，避免用户态死循环空转
fd_set set;
FD_ZERO(&set);        // 每次调用前都得重建位图（select 返回时会覆写 set）
FD_SET(conn1, &set);  // 上限固定为 FD_SETSIZE (1024)
FD_SET(conn2, &set);
// 把整个位图拷进内核并睡眠，直到任意一个 fd 就绪
select(maxfd + 1, &set, NULL, NULL, &timeout);select.c

这一步把“用户态自己轮询”变成了“内核通知就绪”，CPU 不再白白空转。但 select 在使用上有三个明显的限制：

  1. 文件描述符数量上限固定为 1024：它用定长位图 fd_set 存放描述符，编号超过 1023 就放不进去，面对一万个连接根本装不下。
  2. 每次调用都要重新拷贝整份集合：每次进 select 都得把完整的 fd_set 从用户态拷进内核态，哪怕其中大部分连接根本没变。
  3. 内核与用户态仍需全量扫描：内核并不知道究竟哪几个连接有数据，只能把集合从头扫到尾；返回后 fd_set 还会被改写为仅剩就绪位，业务代码每轮都得重新 FD_ZERO 和 FD_SET，一旦漏掉就会丢失监听。

1986 年出现的 poll 把位图换成了结构体数组，顺便把入参 events 和出参 revents 分开：

// 动机：改用结构体数组打破 1024 上限，并分离入参(events)与出参(revents)
struct pollfd fds[2];
fds[0].fd = conn1;  fds[0].events = POLLIN;
fds[1].fd = conn2;  fds[1].events = POLLIN;
// 仍需每次将整个 fds 数组拷进内核并全量扫描
poll(fds, 2, -1);poll.c

数组没有 1024 的硬上限，也不用每轮重建监听集合。但每次调用依然要把整个 pollfd 数组拷进内核，内核也依然要从头到尾扫描全部连接。连接数上万且只有少数几个活跃时，poll 的性能问题和 select 一样。

epoll：记住名单与就绪回调

要补齐 select 和 poll 剩下的两个短板，内核需要多做两件事：第一，把监听名单直接留在内核里，增删改时才操作，不用每次等待都重传；第二，数据到达网卡并进入对应 socket 缓冲区时，内核顺手把这个连接记进一个“已就绪名单”，这样等待方来取时只需要看那份就绪名单，不必扫描全部连接。

2002 年 Linux 引入的 epoll 正是用这三个部件把这两件事落地的：用红黑树长期维护已注册的 fd，用回调函数在数据到达时把对应项挂进就绪链表，epoll_wait 只负责把就绪链表里的事件取出来。

// 动机：名单常驻内核红黑树，事件靠回调入就绪链表，省掉重复拷贝和全量扫描
int epfd = epoll_create1(0);                    // 1. 创建 epoll 实例
epoll_ctl(epfd, EPOLL_CTL_ADD, conn, &ev);      // 2. 注册一次，长期保存在红黑树
int n = epoll_wait(epfd, events, 128, -1);      // 3. 只拷回已经就绪的 n 个事件epoll.c

当一万个连接里只有 3 个活跃时，epoll_wait 只返回这 3 个事件，省掉了无意义的全量拷贝和全量扫描。

epoll 的边界与代码复杂度

实际使用中，epoll 也有三个常被忽略的边界：

  1. 性能优势依赖“连接多、活跃少”：如果一万个连接在同一时刻全部就绪，就绪链表里同样有一万个事件，epoll_wait 照样要搬运一万条记录，开销和 poll 接近。
  2. 它只通知“可读写”，不代劳“拷贝数据”：epoll_wait 返回只代表内核缓冲区准备好了，业务线程还得自己调用 read() 把数据从内核拷回用户态。因此 epoll 仍然属于同步 IO 多路复用，而不是像 io_uring 或 Windows IOCP 那样由内核完成整个数据搬运的异步 IO。
  3. 边缘触发（ET）要求一次读空：默认的水平触发（LT）只要缓冲区还有未读数据就会持续通知；边缘触发只在状态从不可读变为可读时通知一次，事件更少，但业务代码必须循环读取直到返回 EAGAIN，否则残留数据不会再触发下次通知。Go 的 netpoll 底层用的就是边缘触发。

效率问题在 epoll 这一层基本解决，但开发体验却一路变差。原本“读请求、查库、写响应”的线性业务，在事件循环里因为数据可能分多次到达，不得不拆成回调和状态机，在多段事件之间手动保存上下文。

模型资源开销代码形态
阻塞读 + 多线程线程数随连接数膨胀线性代码，最直观

Go netpoll 如何兼顾写法与效率

Go 运行时做了一层反转：把线性写法留给业务代码，把事件循环和阻塞等待收进底层调度器。业务代码里写出来的依然是：

// 动机：业务保留线性阻塞写法，底层由 netpoll 托管非阻塞 socket 与 epoll/kqueue
conn, _ := ln.Accept()
n, _ := conn.Read(buf)   // 无数据时 gopark 挂起当前 G，不卡死系统线程
handle(buf[:n])go-netpoll-server.go

在底层，所有网络 socket 在创建时都会被设成非阻塞并注册进系统的多路复用器（Linux 下是 epoll，macOS 下是 kqueue）。当 conn.Read 暂时没有数据时，当前 goroutine 不会被卡死在系统调用里，而是通过 gopark 挂起为等待状态，把控制权交回调度器去跑其他 goroutine；等内核返回就绪事件，调度器再把原 goroutine 放回运行队列继续往下执行。阻塞从操作系统线程搬到了用户态。

按仓库 examples/go/concurrency/ 下的两组本机实测对照：

  • netpoll-sockets 起 300 个 goroutine 同时阻塞读 socket（总计 302 个 goroutine），在 GOMAXPROCS=2 下进程只用了 5 个系统线程，两个 P 都处于空闲等待。
  • gmp-syscall-handoff 起 4 个 goroutine 阻塞读 /dev/urandom，线程数从 2 涨到了 7，因为普通文件不支持 epoll/kqueue，只能让系统线程真实卡进内核。

同为“阻塞读”，socket 几乎不额外占系统线程，普通文件却必须赔上真实线程，分水岭就在是否能走 netpoll 这条多路复用链路。

三个常见误区

  1. “epoll 的复杂度是 O(1)”：epoll_wait 取事件的开销与就绪连接数成正比，即 O(就绪数)，一万个连接同时活跃时照样要处理一万次；epoll_ctl 操作红黑树则是 O(log n)。它快在“每次只处理活跃连接”，并不是常数复杂度。
  2. “epoll 用 mmap 零拷贝共享就绪链表”：在主流 Linux 内核实现里，epoll_wait 是通过 copy_to_user 把就绪事件拷贝给用户态的，并没有用 mmap 共享内核链表。真正省掉的是每次系统调用都拷贝全量 fd 集合的开销。
  3. “IO 多路复用就是用一个线程管多个连接”：单靠非阻塞 IO 的大循环就已经能用一个线程管多个连接了。多路复用真正复用掉的是系统调用次数，把一轮轮反复询问变成一次等待、由内核代为筛选。

从阻塞线程到非阻塞轮询，再到 select、poll、epoll 和用户态调度，每一层改进都在解决上一层暴露出的具体限制：先解决“单线程卡死”，再解决“线程数过多”，接着解决“用户态空转”和“内核全量扫描”，最后用 goroutine 与 netpoll 把事件回调的复杂度从业务代码里剥离出来。
