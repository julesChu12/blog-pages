从一段卡住的代码到 epoll：IO 模型是怎么一步步长出来的

2026 年 11 月 26 日
|

这篇文章不打算先告诉你 select、poll、epoll 是什么，再让你记住它们的优缺点。我想反过来：从一段你随手就能写出来的服务器代码开始，让它一步步遇到问题，你自己想办法解决，最后才发现——你想出来的那个东西，历史上早就有人做出来了，它叫某个名字。

这样每个名词出场时，你都已经知道它为什么存在。

一段只有一个客户端时完全正确的代码

ln, _ := net.Listen("tcp", ":8080")
conn, _ := ln.Accept()      // 等一个客户端连上来
buf := make([]byte, 1024)
n, _ := conn.Read(buf)      // 等它发数据
handle(buf[:n])             // 处理

一个客户端的时候，这段代码没有任何问题。Accept 等到连接，Read 等到数据，handle 处理。线性、直白，谁都会写。

第二个客户端来了，它卡住了

现在有两个客户端。第一个连上了，但连上之后还没发数据，于是程序停在 conn.Read(buf) 这一行，等着。

就在这时，第二个客户端把数据发过来了。

没人理它。 因为整个程序只有一个线程，而这个线程正卡在第一个连接的 Read 上，出不来。它不知道第二个连接有数据，也没空去看。

把这件事浓缩成一句话，后面所有内容都围着它转：

Read 在等数据的时候，这个线程什么都干不了。

注意，这不是 Go 的毛病，C、Java、Python 全一样。这是”阻塞读”这个动作本身的性质。

你自己能想到的两条路

问：怎么让一个程序同时照顾两个连接？

先别往下看，自己想一想。大概率你会想到两条路：

路一：再开一个线程。 一个线程盯第一个连接，另一个盯第二个。谁的数据来了，各自的线程处理各自的。

路二：让 Read 别等。 没数据就立刻返回，告诉我”现在没有”，我先去看看别的连接，过会儿再回来问。

这两条路都是对的。而且它们不是我先塞给你的两个名词——是你自己先想到的两个办法，历史上它们真的先后被用了出来。第一条叫多线程，第二条叫非阻塞 IO。

下面分别走一遍，看它们各自在哪断掉。

路一：一人盯一个，断在”人太多”

多线程最直观。10 个连接开 10 个线程，100 个开 100 个，都没问题。

但连接涨到 10000 个呢？每个线程不是免费的：

  • 每个线程要自己的栈。Linux 默认一个线程栈 8MB（虚拟内存），10000 个就是 80GB 虚拟地址空间。
  • 内核要为每个线程维护调度信息，线程切换要保存、恢复现场，还要进内核。
  • 10000 个线程轮流抢 CPU，光切换就吃掉大量时间。

一台机器扛几千个线程就到头了。连接数 = 线程数，这条路被线程的数量上限卡死。

这正是 1999 年 Dan Kegel 提出的著名问题：一台服务器怎么同时扛住一万个连接？史称 C10K。

路二：让 Read 别等，断在”问得太累”

非阻塞 IO 把 Read 改成”没数据立刻返回”。于是一个线程就能照顾所有连接：

for {
    for _, conn := range conns {
        n := read(conn)      // 没数据立刻返回，不卡
        if n > 0 {
            handle(...)
        }
    }
}

一个线程，一万个连接，内存和线程问题全没了。

但新问题来了：这个循环在空转。 一万个连接，绝大多数时刻没数据。每问一次是一次系统调用，大约微秒级；一万个问一轮就是十毫秒级。CPU 100% 占着，可一万次里九千九百多次是白问。

而且这里有个两难：

  • 问得勤 → 响应快，但 CPU 全烧在”问”上。
  • 问得慢（比如每轮之间睡 10ms）→ CPU 省了，但数据到了最多要等 10ms 才被发现。

用 CPU 换延迟，两头都不划算。

一个自然冒出来的问题

走到这里，你会自然地想：

挨个问太累了。能不能我只说一次”我要盯这些连接”，之后谁有数据了，内核直接叫我，没数据我就睡着，不占 CPU？

这句话，就是 select。

不是”select 是一个监视文件描述符集合的系统调用”这种定义——是你自己提出的需求，select 只是这个需求的名字。1983 年 BSD 就把它做出来了。

它的用法正是你想的那样：把要盯的连接交给内核，内核替你等，任何一个就绪就把你叫醒。

fd_set set;
FD_ZERO(&set);
FD_SET(conn1, &set);
FD_SET(conn2, &set);
select(maxfd + 1, &set, NULL, NULL, &timeout);  // 睡到有人就绪

这一步是真正的分水岭：从”你主动挨个问”，变成”内核主动通知你”。CPU 不再空转，延迟也最低。

select 的三个麻烦

但 select 用起来有三个具体的麻烦，每个都能逼出下一代。

麻烦一：放不下。 select 用一个叫 fd_set 的位图存连接，这个位图固定 1024 位。也就是说连接编号超过 1023 就放不进去。一万个连接？对不起，放不下。这不是”慢”，是”装不下”。

麻烦二：每次都要重新交名单。 每次调用 select，都得把整个 fd_set 从你的程序拷进内核。哪怕你只盯 3 个连接，也要走一遍这个拷贝。连接越多，每次拷得越多。

麻烦三：内核挨个查。 内核拿到位图，不知道你关心哪几个，只能从头到尾扫一遍，看谁就绪了。一万个连接里只有 3 个有数据，它也得查一万个。

还有一个容易踩的坑：select 返回时会把 fd_set 改写，只剩就绪的那几位。所以下一轮必须重新 FD_ZERO、重新 FD_SET。忘了重建，就永远等不到——这是个经典 bug。

poll：只修了”放不下”

1986 年 poll 出来了。它把位图换成了一个结构体数组：

struct pollfd fds[2];
fds[0].fd = conn1;  fds[0].events = POLLIN;
fds[1].fd = conn2;  fds[1].events = POLLIN;
poll(fds, 2, -1);

数组想开多大开多大，“放不下”解决了。而且输入输出分开（events 是你关心的，revents 是内核填的结果），不用每次重建。

但是——麻烦二和麻烦三一个都没修。 每次调用还是要把整个数组拷进内核，内核还是要挨个扫一万个，你回来还是要自己遍历一万个找就绪的。

所以 poll 只是把 select 的”容量”和”易用性”修好了，最要命的”每次全量拷贝 + 全量扫描”原封不动。 连接一多，它和 select 一样慢。

如果你是内核设计者

现在问题非常具体了，就两条：

  1. 每次都要重新告诉内核”我盯哪些连接”——能不能让它记住？
  2. 内核每次都要挨个查一万个——能不能别查？

先别急着看 epoll 的答案。如果你来设计，你会怎么做？

针对第一条：让内核记住名单，那我注册一次就够了，之后不用再交。内核得有个数据结构存这些连接，要能快速增、删、查。连接数不定、增删频繁——你会想到用一棵树（查找、插入、删除都是 O(log n)）。

针对第二条：别每次查，那就在数据到达的那一刻，顺手记一笔。数据到内核时本来就要唤醒对应的连接，那就在这时把”这个连接就绪了”记到一个名单上。等我要的时候，直接把这个名单给我，根本不用查。

你看，这两个想法一出来，epoll 的三个核心部件就全齐了：

  • 存名单的树 → 红黑树
  • 数据到达时顺手记一笔 → 回调
  • 记下来的就绪名单 → 就绪链表

红黑树、回调、就绪链表，不是三个要背的词，是你刚才那两个问题的答案。

epoll：把三个部件拼起来

2002 年 Linux 把这套做出来了，就是 epoll。三个调用，正好对应你想的三步：

int epfd = epoll_create1(0);                    // 建一个实例
epoll_ctl(epfd, EPOLL_CTL_ADD, conn, &ev);      // 注册一次，内核记住
int n = epoll_wait(epfd, events, 128, -1);      // 要的时候，只返回就绪的
  • epoll_ctl 把连接加进红黑树，只交一次，之后 epoll_wait 不再碰名单。→ 解决麻烦二。
  • 数据到达时，内核通过回调把该连接挂进就绪链表。→ 解决麻烦三的”查”。
  • epoll_wait 只看就绪链表：空就睡，不空就把里面的拷出来直接返回。→ 你不用再遍历一万个。

一万个连接里只有 3 个活跃，epoll 就只处理这 3 个。这就是它快的全部原因。

到这里，epoll 为什么快，不用我解释，你自己就能推出来——因为你就是照着问题把它设计出来的。

epoll 没解决的三件事

但别急着觉得 epoll 完美。它有三个边界，理解了才算真懂。

边界一：它的快有前提。 epoll 快，是因为”就绪的远少于注册的”。如果一万个连接同时全部活跃，就绪链表里也是一万个，epoll_wait 要拷一万个，和 poll 一样慢。所以”epoll 比 select 快一百倍”这句话，只在”连接多、活跃少”时成立。

边界二：它只告诉你”就绪”，不帮你”搬数据”。 epoll_wait 返回”这个连接可读了”，但数据还在内核缓冲区，你还得自己调 read() 把它搬进你的内存——这一步仍然是你干、仍然会阻塞。所以 epoll 不是异步 IO，它是”同步 IO + 高效等待”。真正的异步（内核连搬数据都替你做完）是后来的 io_uring、Windows 的 IOCP。

边界三：边缘触发很容易写错。 epoll 默认”水平触发”：只要还可读，每次都通知你。它还有个”边缘触发”模式：只在”从没数据变有数据”那一刻通知一次。后者事件少、更快，但要求你一次把数据读干净（读到返回”没数据了”为止），否则剩下的数据永远躺在那，再也没人通知你。Go 用的就是边缘触发，所以它的读代码里有个循环，读不干净就接着读。

真正的代价：代码没法看了

走到 epoll，效率问题解决了。但回头看，有个东西一路在丢。

最早的阻塞代码是线性的：读请求 → 查数据库 → 写响应，顺着写下来就行。

可在 epoll 的事件循环里，一个连接的数据可能分好几次到。你得把”读请求 → 查库 → 写响应”这个流程拆成几段，每段之间把进度存到一个结构体里，等下次事件来了再续上。一个本该顺着写的业务，被拆成了状态机。

这就是为什么早年写高并发服务器那么痛苦：Node.js 的回调地狱、C 语言 epoll 服务器动辄几千行。每一代都在用”编程复杂度”换”资源效率”。

方案资源代码
阻塞 + 多线程线程数 = 连接数，扛不住最简单，线性
非阻塞轮询省线程循环 + 空转
select / poll / epoll一个线程管海量连接事件循环 + 状态机，最难

效率到位了，代码却没法看了。能不能两个都要？

Go：把简单还回来

Go 做了一件反方向的事：让你照第一代的样子写代码，底下跑 epoll 的机制。

你写的还是线性的：

conn, _ := ln.Accept()
n, _ := conn.Read(buf)   // 看起来在"等"
handle(buf[:n])

但 conn.Read 底下不是真的把线程卡死。数据没到时，Go 把当前这个 goroutine 挂起，让线程去跑别的 goroutine；数据到了，epoll 通知 runtime，把那个 goroutine 唤醒接着跑。“阻塞”从内核层面搬到了用户态。

于是一个连接一个 goroutine，而 goroutine 初始栈只有 2KB，不是线程的 8MB。一万个连接，线程还是只有几个。

这不是空话，是实测过的（示例在仓库 examples/go/concurrency/）：

  • 302 个 goroutine 全部阻塞在 socket 读上（netpoll-sockets），GOMAXPROCS=2，线程只有 5 个，两个 P 全闲着。
  • 对比 4 个 goroutine 读文件（gmp-syscall-handoff），线程从 2 涨到 7——因为普通文件不能用 epoll，只能让线程真的陷进内核。

同样是”阻塞”，socket 上的阻塞几乎不要钱，文件上的阻塞要赔线程。差别就在有没有走 epoll 这条多路复用的路。

这就是整个 GMP 调度存在的意义：它是那个”把简单还给你”的实现。

三个流传很广的错误说法

最后纠正三个网上常见、但经不起推敲的说法，面试时尤其要小心。

说法一：“epoll 是 O(1)。” 不对。epoll_wait 是 O(就绪数)，epoll_ctl 操作红黑树是 O(log n)。一万个全活跃时它也是 O(一万)。它的优势是”就绪远少于注册”，不是常数时间。

说法二：“epoll 用 mmap 共享就绪链表，零拷贝。” 不准确。现代内核里 epoll_wait 是通过 copy_to_user 把就绪事件拷出来的，没有 mmap 共享。真正省掉的是”每次拷贝整个 fd 集合”，不是”零拷贝事件”。

说法三：“IO 多路复用就是用一个线程管多个连接。” 没说到点上。非阻塞 IO 早就做到一个线程管多个连接了。多路复用真正复用掉的是系统调用次数：把”问一万次”变成”问一次，内核替我筛”。

一句话串起全文：

CPU 太贵，不能干等 IO → 一个连接一个线程，线程又太贵 → 让一个线程管所有连接，但得解决”怎么知道谁好了” → 从自己挨个问（非阻塞），到交给内核等（select/poll），再到内核记住名单、就绪才通知（epoll）→ 效率够了，代码却没法看 → 最后用用户态调度，把”线性代码”还给你（goroutine）。

每一个名词，都是上一个问题的答案。
