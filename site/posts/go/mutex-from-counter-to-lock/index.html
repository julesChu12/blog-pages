从 counter++ 到 Mutex：重新理解 Go 的锁

2026 年 11 月 24 日
|

复习 Go 并发时，我一度觉得锁只是 mu.Lock() / mu.Unlock() 两行模板。直到把 counter++ 拆开、用 -race 跑了一遍，才意识到它保护的不是一行代码，而是一段不能被打断的状态变化。

本文从一次丢失更新出发，依次走过临界区、atomic/CAS、Mutex 的公平性、RWMutex 的读写边界和工程上的死锁。语言行为以 Go 规范和官方文档为准；涉及 state 位、饥饿模式和 readerCount 的部分，以 Go 1.25.8、macOS arm64 为实现基线，具体数值可能随版本和机器变化。可运行的实验集中在 examples/go/concurrency/，并同步在公开仓库 blog-code 的 go/concurrency 目录。

counter++ 不是一步

开头的复现代码可以直接保存为 main.go 运行：

package main

import (
	"fmt"
	"sync"
)

func main() {
	// 100 个 goroutine，每个对同一个 counter 自增 1000 次。
	const goroutines = 100
	const perGoroutine = 1000

	var counter int       // 共享变量：这里故意不加任何同步
	var wg sync.WaitGroup // 等待所有 goroutine 结束

	for range goroutines {
		wg.Go(func() {
			for range perGoroutine {
				counter++ // 读 counter、加一、写回：三步不是原子的
			}
		})
	}

	wg.Wait() // 等所有 goroutine 结束后再读 counter
	fmt.Println("expected:", goroutines*perGoroutine)
	fmt.Println("actual:  ", counter)
}
go run "main.go"

本机一次运行结果：

expected: 100000
actual:   47546

再跑一次可能变成 89307、39178，甚至更接近 100000。结果不稳定，是因为 counter++ 在机器层面不是一步：

读 counter → 加一 → 写回

两个 goroutine 可能同时读到 100，都算出 101，都写回 101：

G1: 读 counter = 100
G2: 读 counter = 100
G1: 写回 101
G2: 写回 101   ← G1 的结果被覆盖

两次自增，最终只增加了一次。这就是丢失更新。

用竞态检测器运行，会直接指出读和写冲突：

go run -race "main.go"
WARNING: DATA RACE

这里要区分两个概念：

概念含义-race 能发现吗
数据竞争并发读写同一内存且没有同步能
逻辑竞态每一步都同步了，但组合起来不原子不能

counter++ 属于前者。而后面库存扣减的 if stock > 0 { stock-- }，即使每一步都用了原子操作，也可能因为“检查”和“扣减”被拆开而出错，属于后者。

临界区：锁保护的是不变量

Mutex 的基本用法很简单：

var mu sync.Mutex // 保护 counter；零值 Mutex 就是未加锁状态
var counter int

mu.Lock()   // 进入临界区：同一时刻只有一个 goroutine 能到这里
counter++   // 读、加、写被整体保护
mu.Unlock() // 离开临界区，必须和 Lock 配对

完整可运行版本见 examples/go/concurrency/counter-mutex/main.go，输出在下面。

用 defer 可以保证异常路径也解锁：

// increment 把“加锁、自增、解锁”收在一个函数里；
// defer 保证中途 return 或 panic 时也会解锁。
func increment() {
	mu.Lock()
	defer mu.Unlock() // 函数返回前执行，不在循环里跨迭代
	counter++
}

修复后的计数器示例（examples/go/concurrency/counter-mutex/main.go）在 -race 下运行：

expected: 100000
actual:   100000

但锁要保护的不是“某个变量”，而是一段业务不变量。examples/go/concurrency/transfer-mutex/main.go 里两个账户互相转账，要求总额始终不变：

// 固定按 id 从小到大加锁，避免 A->B 与 B->A 形成循环等待。
first, second := from, to
if first.id > second.id {
	first, second = second, first
}

first.mu.Lock()
defer first.mu.Unlock()
second.mu.Lock()
defer second.mu.Unlock()

// 两把锁都拿到后再检查余额：检查和扣减不会被其他转账插队。
if from.balance < amount {
	return false
}

// 扣款和入账在同一个临界区，保证 A+B 的总额不变。
from.balance -= amount
to.balance += amount
return true

运行结果：

initial total: 10000
final total:   10000
invariant:     true

这里有三层保护：

  1. 检查余额和扣减在同一个临界区，避免 check-then-act 被插队。
  2. 两个账户都加锁，否则“钱从 A 扣了、还没加到 B”的窗口会破坏总额。
  3. 固定按 id 顺序加锁，否则 A→B 和 B→A 会互相等待。

第 3 点不是风格问题，而是死锁问题。examples/go/concurrency/lock-order-deadlock/main.go 故意让两个方向交叉加锁：

go run examples/go/concurrency/lock-order-deadlock/main.go deadlock
fatal error: all goroutines are asleep - deadlock!

运行时会打印所有 goroutine 的栈，其中两个卡在 sync.Mutex.Lock，各自持有对方需要的那把锁。修复版按 id 排序：

go run examples/go/concurrency/lock-order-deadlock/main.go fixed
a=100 b=100 total=200

死锁的四个条件里，固定加锁顺序打破的是“循环等待”。

不用锁：atomic 与 CAS

如果临界区只是一个变量的单步操作，可以用 sync/atomic：

var counter atomic.Int64 // 用原子类型，避免读写撕裂
counter.Add(1)           // Add 本身原子，但只覆盖“加”这一步

examples/go/concurrency/counter-atomic/main.go 的结果同样是：

expected: 100000
actual:   100000

但 atomic.Add 只保证“加”这一步原子，不保证“检查 + 加”整体原子。库存扣减：

// 错误写法：Load 和 Add 各自原子，但“检查 + 扣减”整体不原子。
if stock.Load() > 0 {
	stock.Add(-1) // 这中间可能被其他 goroutine 插队
	sold.Add(1)
}

examples/go/concurrency/stock-oversell/main.go 的一次运行：

naive  sold=112  stock=-12
cas    sold=100  stock=0

naive 版卖出了 112 件、库存 -12。检查时大家都看到 stock > 0，于是都进入了扣减流程。

纯 atomic 的正确写法是 CAS 循环：

for {
	old := stock.Load() // 读取当前库存
	if old <= 0 {
		return false // 没库存，直接放弃
	}
	// 只有库存仍等于 old 时才扣减；否则说明被别人改过，重试。
	if stock.CompareAndSwap(old, old-1) {
		return true
	}
}

examples/go/concurrency/stock-cas/main.go 的结果：

sold=100 stock=0 retries=15

retries 记录的是 CAS 失败后重试的次数，非零说明竞争真实发生过。规律很简单：单变量、单步操作可以 atomic；需要“检查再修改”时，用 CAS 循环或锁。

锁的范围：wide 与 narrow

知道怎么加锁后，下一个问题是“加多大”。examples/go/concurrency/lock-scope/main.go 用 10 个 worker 对比两种写法，每个 worker 都有一次 50ms 的慢操作：

// wide：慢操作也在临界区内，其他 worker 只能排队等锁。
s.mu.Lock()
defer s.mu.Unlock()
time.Sleep(50 * time.Millisecond) // 模拟 RPC、日志或磁盘 I/O
s.n++                             // 真正需要互斥的只有这一步

// narrow：慢操作放在锁外，多个 worker 可以并行。
time.Sleep(50 * time.Millisecond)
s.mu.Lock() // 只保护共享状态
s.n++
s.mu.Unlock()

实测：

mode=wide   workers=10 count=10 elapsed=510ms
mode=narrow workers=10 count=10 elapsed=50ms

wide 把 50ms 的慢操作也锁住，10 个 worker 完全串行；narrow 只锁 n++，慢操作重叠执行。

规则：锁的范围要刚好覆盖共享状态的读写，不要覆盖 I/O、RPC、日志和耗时计算。 但不能无脑缩小——如果慢操作依赖锁内读到的状态，缩小后必须重新检查或用版本号/CAS，否则又会变成 check-then-act。

同一个示例还有 recursive 模式：

func (s *stats) incRecursive() {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.incRecursive() // 已经持锁，又调用自己再次 Lock
}

运行结果：

fatal error: all goroutines are asleep - deadlock!

Go 的 Mutex 不可重入，不记录 owner，同一个 goroutine 第二次 Lock 会等自己。修复方式是把“加锁的公开方法”和“假设已持锁的内部方法”拆开。

Mutex 内部：一个 state 管四件事

sync.Mutex 在 Go 1.25.8 里是 internal/sync.Mutex 的包装，核心只有一个 int32 的 state 和一个信号量。state 的低 3 位是标志，其余位是等待者数量：

位权重含义
bit 01已加锁
bit 12已有等待者被唤醒/正在自旋
bit 24饥饿模式
bit 3+8等待者数量

比如 state = 9 = 8 + 1，表示“已加锁 + 1 个等待者”。examples/go/concurrency/mutex-state/main.go 在一个受控时序里打印出：

初始:         state= 0 locked=false woken=false starving=false waiters=0
加锁后:       state= 1 locked=true  woken=false starving=false waiters=0
有等待者:     state= 9 locked=true  woken=false starving=false waiters=1
解锁后:       state= 2 locked=false woken=true  starving=false waiters=0
等待者拿到:   state= 1 locked=true  woken=false starving=false waiters=0
等待者释放:   state= 0 locked=false woken=false starving=false waiters=0

这里有两个容易忽略的点：

  • 解锁只唤醒等待者，不把锁交给它。 state=2 表示锁已经释放，但等待者还没运行；新来的 goroutine 可以先抢到锁。examples/go/concurrency/mutex-starvation/main.go 把这一步固定下来：
等待者入队:     state= 9 locked=true  woken=false starving=false waiters=1
新来的先抢到:   state= 3 locked=true  woken=true  starving=false waiters=0
等待超 1ms:     state=13 locked=true  woken=false starving=true  waiters=1
等待者拿到:     state= 1 locked=true  woken=false starving=false waiters=0
等待者释放:     state= 0 locked=false woken=false starving=false waiters=0

state=3 说明新来的 goroutine 已经拿到锁，而 woken 标记还没清。被唤醒的等待者真正运行后，发现锁被占，只能重新排队；如果累计等待超过 1ms，就把 starving 置上（state=13 = 8 + 4 + 1）。

  • 饥饿模式直接把锁交给队首。 正常模式下解锁会调用 Semrelease 唤醒一个等待者，但等待者还要再抢一次；饥饿模式下 handoff=true，解锁者直接把锁交接出去，新来的 goroutine 一律排队。代价是吞吐低，所以等待者拿到锁后，只要它是最后一个等待者，或者本次等待不足 1ms，就退出饥饿模式。

woken 位的作用是避免重复唤醒：自旋中的 goroutine 可能马上拿到锁，解锁者看到它就不用再叫醒别人。

RWMutex：读多写少的代价

配置缓存这类场景，读远多于写。RWMutex 允许多个读者同时进，写者独占：

var rw sync.RWMutex

rw.RLock()   // 读锁：多个读者可以同时持有
// 读取配置；不要修改共享状态
rw.RUnlock() // 释放读锁

rw.Lock()    // 写锁：写者独占，读者和其他写者都要等
// 更新配置
rw.Unlock()

内部用一个 readerCount 同时表达两件事：

  • >= 0：当前活跃读者数
  • < 0：有写者在等待或持有锁

写者到来时减去 rwmutexMaxReaders（1 << 30），把计数推进负数区；之后新的 RLock 加一仍是负数，只能阻塞。写者释放时加回这个常量，返回值正好是被挡住的读者数。

examples/go/concurrency/rwmutex-cache/main.go 的实测：

mode=readers readers=5 elapsed=50ms value=v1
mode=writers writers=3 elapsed=150ms value=v2

5 个读者各 50ms，总耗时约 50ms；3 个写者各 50ms，总耗时约 150ms。读锁并行、写锁互斥。

写者优先模式：

0s     reader-1 获得读锁
10ms   writer 等待写锁
20ms   reader-2 尝试读锁
50ms   writer 获得写锁
50ms   reader-1 释放读锁
100ms  writer 释放写锁
100ms  reader-2 获得读锁
100ms  reader-2 释放读锁

reader-2 在 20ms 就想读，但直到 100ms 写者释放后才拿到锁——即使此时 reader-1 还在读。这是写者优先：一旦写者开始等待，新读者也要排队，避免写者被源源不断的读者饿死。代价是读延迟变差。

RWMutex 有两个必须避开的坑：

  • 递归 RLock：持读锁时再次 RLock，如果中间有写者等待，第二次读锁会阻塞；写者又在等第一次读锁释放，形成环。
  • 读锁升级写锁：先 RLock 再 Lock，写者会等包括自己在内的读者退出，等于自己等自己。正确做法是先释放读锁，再拿写锁，然后重新检查状态；如果“读—判断—写”必须原子，直接用普通 Mutex。

工程边界

除了死锁和锁范围，日常还需要注意：

  • 循环里不要用跨迭代的 defer Unlock：
for i := 0; i < 2; i++ {
	mu.Lock()
	defer mu.Unlock() // 第一轮结束后锁仍被持有，第二轮 Lock 卡住
	fmt.Println("iteration", i)
}

运行结果：

iteration 0
fatal error: all goroutines are asleep - deadlock!

因为 defer 绑定的是函数返回，不是循环迭代结束。把单轮逻辑抽成函数，让 defer 随函数返回执行：

for _, item := range items {
	updateOne(item) // 每轮调用一个独立函数
}

func updateOne(item Item) {
	mu.Lock()
	defer mu.Unlock() // 函数返回时解锁，不会跨迭代
	update(item)
}
  • 不要拷贝含锁的结构体。拷贝后是两个独立的锁，互斥直接失效。
  • 不要在锁内做慢操作。RPC、日志、磁盘 I/O 会把并发拖成串行。
  • 不要依赖 -race 证明没问题。它只覆盖实际执行到的路径，也抓不到逻辑竞态。

选型上可以记住一张表：

场景选择
一组字段要一起修改，或需要 check-then-actMutex
单个计数器、开关、指针替换atomic
读远多于写，且读操作本身不轻RWMutex
传递事件、所有权、任务编排channel
请求取消、超时Context

锁不是越用越多越好，也不是越细越好。它保护的是“不能被拆开的状态变化”，范围刚好覆盖不变量即可。
