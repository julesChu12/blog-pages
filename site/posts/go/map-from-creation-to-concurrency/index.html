从创建到并发访问：重新理解 Go Map

更新于: 2026 年 11 月 18 日
|

日常使用 map 时，m[key] 和 m[key] = value 看起来很简单；真正需要仔细判断的，是赋值后是否共享、删除后空间如何处理、遍历中修改是否影响结果，以及并发访问该怎样保护。

本文以 Go 语言规范描述可观察行为；涉及 Swiss Map、容量增长、编译器和 sync.Map 内部结构的部分，以 Go 1.25.8、macOS arm64、默认实验配置为观察基线。实现细节会随版本、架构和构建配置变化。

文中的配套例子如下，也保存在源码仓库的 examples/go/map-lifecycle/main.go。读者可以把代码保存为 main.go 后直接运行：

package main

import "fmt"

func main() {
	// hint 表示预期条目数量；创建时 map 仍然为空。
	items := make(map[int]int, 8)
	fmt.Println("创建后长度:", len(items))

	// 插入 8 个不同的 key，记录操作前后的可观察状态。
	for key := 1; key <= 8; key++ {
		items[key] = key * 10
	}
	fmt.Println("插入 8 项后长度:", len(items))

	// 新增第 9 个 key；具体增长路径取决于 Go 版本和编译条件。
	items[9] = 90
	fmt.Println("插入第 9 项后长度:", len(items))

	// 更新已存在的 key，不会增加 map 元素数量。
	items[3] = 300
	value, ok := items[3]
	fmt.Println("更新后 key 3:", value, ok, "长度:", len(items))

	// 查找不存在的 key，得到 value 的零值和 false。
	value, ok = items[99]
	fmt.Println("不存在的 key 99:", value, ok)

	// 删除指定 key，之后该 key 不再存在。
	delete(items, 4)
	_, ok = items[4]
	fmt.Println("删除 key 4:", ok, "长度:", len(items))

	// 赋值后的 alias 与 items 引用同一张 map。
	alias := items
	alias[1] = 11
	fmt.Println("通过 alias 更新 key 1:", items[1])

	// 复制条目到新 map；int value 是值复制，后续修改互不影响。
	snapshot := make(map[int]int, len(items))
	for key, value := range items {
		snapshot[key] = value
	}
	snapshot[1] = 999
	fmt.Println("原 map 与快照的 key 1:", items[1], snapshot[1])

	// 只汇总 value，不依赖 map 的遍历顺序。
	sum := 0
	for _, value := range items {
		sum += value
	}
	fmt.Println("剩余 value 总和:", sum)
}
go run "main.go"

本机运行结果：

创建后长度: 0
插入 8 项后长度: 8
插入第 9 项后长度: 9
更新后 key 3: 300 true 长度: 9
不存在的 key 99: 0 false
删除 key 4: false 长度: 8
通过 alias 更新 key 1: 11
原 map 与快照的 key 1: 11 999
剩余 value 总和: 681

这些结果验证的是 Go 代码能观察到的行为；len 不能直接告诉我们底层 Table 容量，也不能单凭输出证明发生了哪次分配或扩容。

赋值、读取与 nil map

a := map[string]int{"Go": 1}
b := a

b["Go"] = 2
fmt.Println(a["Go"]) // 2

b = map[string]int{"Go": 3}
fmt.Println(a["Go"], b["Go"]) // 2 3

赋值复制 map 值，不复制整份映射数据。最初 a 和 b 引用同一个 map；给 b 重新赋值后，只有 b 指向新 map。函数接收 map 参数时也有相同的共享关系。

查找不存在的 key 会得到 value 类型的零值；用两个返回值可以区分“不存在”和“值就是零值”：

m := map[string]int{"Go": 0}

v, ok := m["Go"]    // 0, true
v, ok = m["Redis"]  // 0, false

对于合法可哈希的 key，nil map 可以读取和删除，但写入会 panic。make(map[K]V, hint) 的 hint 是预期元素数量的提示，创建后 len(m) 仍为 0；它不是 slice 的长度，也没有可用的 cap(m)。

key、哈希与相等比较

map 的 key 类型必须支持 == 和 !=。例如 string、int，以及元素可比较的数组都可以作为 key；slice 和 map 不能直接作为 key。

哈希用于缩小查找范围，最终还要比较完整 key：不同 key 可能得到相同的哈希或哈希片段。接口类型可以作为 key，但如果接口实际保存了不可比较的动态值，例如 []int，相关 map 操作可能在运行时 panic。

版本边界：从 hmap 到 Swiss Map

Go 1.24 发布说明宣布内置 map 默认采用基于 Swiss Table 的新实现；我们下文分析的是 Go 1.25.8 的默认路径。Go 1.24 和本机 1.25.8 还提供 GOEXPERIMENT=noswissmap 构建选项，可以切回旧实现，因此排查实际程序时应同时确认 Go 版本与构建配置。

Go 1.23 默认实现使用 hmap、bucket 和 overflow bucket。以 Go 1.23.12 的源码为例：

hmap
├── count：当前元素数
├── B：主 bucket 数量为 2^B
├── hash0：哈希种子
├── buckets：当前 bucket 数组
└── oldbuckets：增长期间保留的旧 bucket 数组

主 bucket → overflow bucket → 更多 overflow bucket（按需连接）

旧版每个 bucket 可保存最多 8 组键值；哈希帮助选择主 bucket，bucket 内的 tophash 帮助筛选候选，仍需要比较完整 key。冲突较多时，运行时可能沿 overflow 链继续查找。查询可从 Go 1.23.12 的 mapaccess1 对照。

写入时，如果负载超过阈值，主 bucket 数量通常翻倍；如果 overflow bucket 过多而负载未超过阈值，可能进行等量扩容，重新整理条目但保持主 bucket 数量不变。hashGrow 创建新的 bucket 数组，迁移由后续操作逐步推进；增长期间读取可能根据迁移状态选择旧 bucket。普通删除不会仅因为条目减少就自动缩小主 bucket 数组；等量扩容也不是主 bucket 缩容。Go 1.23.12 的 hashGrow

比较项Go 1.23 默认 hmapGo 1.25.8 默认 Swiss Map
数据组织bucket 数组与 overflow bucketDirectory、Table、Group 和 Slot；小 map 可直接用 Group
冲突处理查找主 bucket 及可能的 overflow 链Table 内通过探测序列查找 Group，结合控制字节筛选
增长新旧 bucket 数组配合，逐步迁移单张 Table 增长或拆分；map 可以包含多张 Table

这些差别属于实现；map 的语言语义不要求业务代码根据版本改写基本读写操作。性能需要针对工作负载测量，不能仅根据版本断言具体业务一定更快。

Go 1.25.8 的 Swiss Map 结构

Go 1.24 起默认的内置 map 基于 Swiss Table；Go 1.25.8 将一个 map 的存储组织为一张或多张 Table。不要把旧版 hmap 的 bucket 和 overflow bucket 结构直接套用到当前实现。

普通路径：Map → Directory → Table → Group → Slot

小 map：  Map → Group → Slot

在当前实现中，Directory 的多个目录项可以指向同一张 Table；每张 Table 管理一个或多个 Group；每个 Group 有 8 个 Slot，每个 Slot 对应一组 key/value。Group 还有 8 字节控制信息，记录 Slot 的 empty、deleted 或已使用状态。

已使用位置的控制字节包含 key 哈希值的低 7 位 H2。在普通 Table 路径中，哈希帮助选择 Table 和起始 Group，H2 用于筛选候选 Slot，随后仍须比较完整 key。对于本机 64 位整数 key 的小 map 读取专用路径，运行时可以直接检查 Group 中已使用的 key；不能认为所有查询都一定先计算哈希。

例如某个 Group 的两个位置保存不同 key，但它们的 H2 恰好相同：

控制信息     H2 = 7          H2 = 7
对应 Slot    10 → "Go"       20 → "Redis"

查询 20 时，两个位置都可能成为候选；比较完整 key 后才能确认第二个位置。这里的 H2 和 Slot 顺序只是示意，不是代码运行后必然得到的值。具体实现见 h1 / h2 和 matchH2。

创建与写入：编译器和运行时各做什么

m := make(map[int]int)
m[10] = 1

编译器会结合逃逸分析和 hint 选择初始化路径。在本机一个不逃逸的局部小 map 实验中，编译器可以准备栈上的 Map 管理结构和 Group；逃逸的小 map 则可能通过 runtime.makemap_small 创建管理结构，并在首次写入时按需准备 Group。动态或较大的 hint 可能走 runtime.makemap / maps.NewMap。这些是具体编译条件下的路径，不代表每次 make 都分配在堆上，也不代表每个 make 都必须调用同一个运行时函数。

在本机的 map[int]int 写入实验中，相关路径调用 runtime.mapassign_fast64：计算哈希，检查已有 key，必要时选择可用 Slot，写入 key 和 H2，再返回 value 的存储位置；调用方完成 value 的写入。读取时对应的实现路径和优化可能不同。

跟着 make 走一遍

配套例子中的：

items := make(map[int]int, 8)
fmt.Println(len(items)) // 0

编译器从 walkMakeMap 选择 Swiss Map，接着 walkMakeSwissMap 根据 n.Esc() 和 hint 生成初始化代码。这里 n 是编译器表示 make 表达式的 IR 节点，n.Len 是 hint 表达式，不是已插入的元素数量。

小 hint 且不逃逸时，编译器可能准备栈上的 Map 和小 Group；小 hint 逃逸时可选择 makemap_small，由 NewEmptyMap 创建 Map 并设置种子。后者路径不急于创建 Group，首次写入时再按需准备。

作为另一个可核对的计算，make(map[int]int, 16) 的 hint 为 16，当前 NewMap 先计算 16 × 8 / 7 = 18 个候选 Slot，再由 newTable 按 2 的幂调整到 32 个 Slot，即 4 个 Group；map 的长度仍为 0。这是当前实现的推导，不是可由 cap 观察的语言保证。

插入、更新、读取分别经过哪里？

items[3] = 30
items[3] = 300
value, ok := items[3]  // 300, true
value, ok = items[99]  // 0, false

在本机 64 位整数 key 的小 map 路径中，写入入口 mapassign_fast64 检查 nil map、计算哈希并选择小 map 或 Table；putSlotSmallFast64 先根据 H2 找候选，再比较完整 key。找到已有 key 就返回它的 value 位置；没有找到则选择空 Slot、写 key 和 H2、增加元素数，再返回 value 位置。我们的本机实验中，调用方使用这个位置写入 30 或 300。

双返回值读取可以对照 mapaccess2_fast64：小 map 分支检查已使用 Slot 的整数 key；普通 Table 分支计算哈希，选择 Table 和 Group，利用 H2 筛选后比较完整 key。找到返回 value 位置和 true；没找到返回零值位置和 false。运行时内部返回指针，业务代码中的 value 获得的是 map 元素值，并不能因此取得 map 元素地址。

Table 如何增长与拆分

普通 Table 的 capacity 表示 Slot 数量，growthLeft 表示重新处理 Table 前的增长余量。对于 Go 1.25.8 中容量大于 8 的全新普通 Table，初始余量按 7/8 计算：32 个 Slot 对应 28 份初始增长余量。

在没有删除标记、只插入不同 key 的简化情形下，插入第 28 个 key 会将余量消耗至 0；继续插入新 key 时才需要进一步处理。删除标记会影响余量，复用与清理也会改变结果，因此不能只用 len 推断何时增长。

当前写入路径在余量不足时先尝试清理合适的删除标记，仍不足才可能 rehash。单张 Table 可按当前实现翻倍增长；当翻倍会超过 maxTableCapacity（1024 个 Slot）时，将该 Table 拆成两张。拆分按哈希高位分配条目，并不保证两边数量完全相同。

Directory 使用 globalDepth 位哈希高位定位目录项，每张 Table 有自己的 localDepth。拆分时，如果旧 Table 的 localDepth == globalDepth，Directory 需要翻倍；否则可以复用已有目录项。一次增长或拆分处理对应 Table 的有效条目，而不是必然迁移整个 map 的所有 Table。

用一张表追踪增长

假设小 map 已存有 8 个不同 key，写入路径需要转入普通 Table：growToTable 创建 16 Slot 的 Table，遍历旧 Group 的有效条目，重新计算哈希并放入新 Table，然后设置 Directory 指向。此后普通读取使用当前结构；迭代中的旧结构另有处理。

假设一张普通 Table 已增长至 32 Slot，且没有删除标记：

已用 27 → growthLeft = 1
插入新 key → 已用 28，growthLeft = 0
再插入一个不存在的 key → 清理尝试后仍不足 → rehash

maxGrowthLeft 计算初始增长余量；PutSlot 在增长余量不足时先尝试清理，再决定是否 rehash；rehash 判断倍增后的容量是否超过 1024。对于 32 Slot，当前实现会创建 64 Slot 的新 Table，并在迁移后重试当前插入。更新已有 key、删除标记和其他类型的专用路径可能改变具体过程。

用目录项理解拆分

假设 Directory 使用 1 位哈希高位：

0 → Table A（localDepth=1）
1 → Table B（localDepth=1）
globalDepth = 1

B 拆分时，原来的一个目录项不够区分两张新表；旧表 localDepth == globalDepth，因此 installTableSplit 先将 Directory 翻倍：

00 → Table A
01 → Table A
10 → Table B-left
11 → Table B-right
globalDepth = 2

此时 A 的 localDepth 仍是 1。若 A 之后拆分，可以复用 00、01，不需要再次扩大 Directory；多个目录项指向同一张 Table 是正常情况。

删除、空 Slot 和内存

delete(m, key) 找到条目后减少元素数，按类型清理相关数据或引用，并更新 Slot 的控制状态。普通 Table 中，如果该 Group 已有 empty Slot，删除位置可标为 empty；如果没有 empty Slot，当前实现使用 deleted 标记，避免破坏可能经过该 Group 的探测路径。小 map 只有一个 Group，删除可直接标为空。

后续插入可沿自己的探测序列复用空位置或合适的 deleted 位置；运行时也可能清理不再需要的删除标记。清理标记不等于缩容。当前实现中的 delete 和 clear 不应被当作保证缩小 Table 或 Directory 的操作。

为什么需要 deleted？

假设 A 和 B 的探测序列从同一个 Group 开始，插入 B 时首个 Group 已满，B 被放到后面的 Group：

Group 0：[A][其他][其他][其他][其他][其他][其他][其他]
              ↓ 继续探测
Group 1：[B][空] ...

如果删除 A 后把它直接标成 empty，查询 B 可能在 Group 0 提前停止；因此这种情况需要 deleted，让查询继续探测。相反，如果删除前该 Group 已经有 empty，当前 table.Delete 可以把删除位置直接设为 empty，并恢复增长余量。

插入时遇到 deleted，会先记录可复用位置并继续探测，以免后面已有相同 key；确认不存在后才可能复用。余量不足时 pruneTombstones 可以检查并清理不再需要的标记，它不移动有效条目，也不保证每次都能清理或避免增长。

如果大量数据已删除、剩余数据需要长期保留，可以在确有内存需求时重建 map：

compact := make(map[string]int, len(old))
for key, value := range old {
    compact[key] = value
}
old = compact

这是浅复制。其他变量若仍引用原 map，它们不会自动转向新 map；并发重建和替换需要同步。原存储只有在没有其他有效引用后才有机会被 GC 回收，回收和归还操作系统的时间也不由赋值操作保证。

遍历时修改：允许顺序操作，不代表并发安全

map 的遍历顺序不受语言规范保证。同一个 goroutine 在 range 循环体中修改 map 是允许的：尚未访问的条目若被删除，不会被返回；新插入的条目可能被遍历到，也可能不会。

Go 1.25.8 的迭代器在被遍历的 Table 增长或拆分后，可以继续参考旧 Table 选择候选 key，再到当前 map 中确认该 key 是否仍存在并取得当前值，从而维护遍历语义。新增条目和特殊 key 还有具体边界，不能把这种实现理解为固定顺序或完整快照。

例如一轮 range 假设先拿到 A，循环体在 B、C 尚未被访问前修改 B、删除 C，并插入 D 导致当前 Table 增长。对原来尚未访问的 B，迭代器在返回时需要取得当前值；C 被删除则跳过；新加入的 D 可以返回，也可以不返回。实际遍历次序不固定，这里只分析假设的顺序。

Iter.Next 维护当前遍历进度；Table 已替换时，grownKeyElem 使用旧结构中的候选 key 在当前 map 中重新查找。旧 Table 是迭代器保留的引用，不是遍历开始时对整个 map 做的一份完整副本。

并发访问：锁保护整个业务操作

初始化完成并安全发布后，多个 goroutine 只读取同一个普通 map 可以不加锁；只要存在并发写入，与之并发的读、写、删除或遍历都需要同步。运行时的 concurrent map read and map write 等检查不是锁，也不能保证检测到每一次数据竞争。

type Counter struct {
    mu   sync.Mutex
    data map[string]int
}

func NewCounter() *Counter {
    return &Counter{data: make(map[string]int)}
}

func (c *Counter) Increment(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key]++
}

读取、计算、写回需要处于同一个临界区；分别加锁读取和写入仍可能丢失更新。go test -race 能帮助发现实际执行路径上的数据竞争，但不能证明多步业务操作具有原子性。

如果需要向调用方返回整个 map，应在锁内创建快照，或明确约定所有访问继续使用同一套同步机制。只在返回前加锁、随后直接返回底层 map，无法保护调用方在解锁后的访问；快照中的指针、slice 等也可能仍然共享。

例如两次访问都单独加锁仍可能丢失更新：A 和 B 先后读到 0，然后先后都写回 1。这未必有数据竞争，但结果与预期的 2 不一致。前面的 Increment 将读、加一、写回放在同一把锁的临界区内；若还需要保护 map 以外的关联状态，也要把业务不变量一起纳入同步设计。

sync.Map：并发安全的单次方法

sync.Map 的 Load、Store、LoadOrStore 和 CompareAndSwap 等方法支持并发访问。它适合特定访问模式，不应仅因接口更短就断定性能更好。Load 后接 Store 不是一个原子复合操作；LoadOrStore(key, expensiveQuery()) 也不能阻止多个 goroutine 在调用前各自执行查询。

本机 Go 1.25.8 的默认实现使用 read、dirty、互斥锁及 entry 中的原子指针：部分 read 命中路径不需要持有内部互斥锁，dirty 查找与更新需要相关协调。read 的键集合和 entry 的当前值是不同层次；这些内部组织不是公开 API 的永久保证。使用后的 sync.Map 不应按值复制，value 指向的可变对象仍需适当同步。

跟着 Load 和 Store 看一次

var cache sync.Map
cache.Store("A", 10)
cache.Store("B", 20)
cache.Load("A")
cache.Load("B")

按本机默认实现、没有并发交错的示意：新增 A、B 先进入 dirty，read 的 amended 标记表示 dirty 还有 read 未包含的 key。第一次读取 A：Load 先查 read，未命中且 amended 时加锁、重新检查 read，再查 dirty 并记录一次 miss。读取 B 又经过 dirty，miss 达到 dirty 的条目数量后，missLocked 将 dirty 提升为 read。这个例子并不保证每种并发时序都恰好经过相同次数。

read 的 map 键集合不直接增删，但它保存的是指向 entry 的指针；entry 中的值可由原子操作更新。当前版本的 Delete 在相关路径中可将 entry 的指针标为 nil；创建 dirty 时已删除的 entry 可能被标为 expunged。重新存入该 key 时，Swap 在持锁路径中恢复 entry 并确保它进入 dirty。这个内部 nil 与业务存入的 nil 值不同：Store("X", nil) 后的 Load("X") 仍返回 ok == true。
