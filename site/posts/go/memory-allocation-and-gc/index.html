从逃逸分析到 GC：重新理解 Go 内存分配与回收

2026 年 11 月 27 日
|

写 Go 业务代码时很少需要直接管理内存的申请与释放，但一到线上服务出现延迟毛刺、容器突然 OOMKilled 或者 pprof 显示 GC 占掉大量 CPU 时，问题往往顺着同一条链路串联起来：对象为什么逃逸到堆上、堆怎么给它分配空间、GC 又在什么时候以什么代价把它收回来。

本文沿这条链路把逃逸分析、三层内存分配器和垃圾回收（GC）整理在一处。语言规范只保证可达对象不被提前回收以及 GOGC/GOMEMLIMIT 的调优语义；文中涉及的规格数量、写屏障缓冲长度和调步器公式均以 Go 1.25.8、macOS arm64 的实现和实测为准，具体数字可能随版本调整。配套实验位于仓库 examples/go/memory/escape-pprof/main.go。

哪些内存不需要 GC 管理

函数内部没有逃逸的局部变量会直接分配在当前 goroutine 的栈上，函数返回时栈帧弹出，内存随即失效，整个过程不需要 GC 参与。只有生命期超出当前函数作用域，或者编译器无法确认能安全留在栈上的对象，才会逃逸到堆上；GC 真正管理的只有堆内存。

实际业务里，很多代码并没有把变量 return 出去，依然悄悄产生了堆分配。为了把“留栈”和“隐蔽进堆”放在一起对照，仓库 examples/go/memory/escape-pprof/main.go 写了三个对照函数，各循环执行 2 万次（加 //go:noinline 是为了防止编译器内联后把调用边界消掉，方便还原真实业务接口调用时的逃逸行为）：

type logItem struct {
	ID   int
	Body [128]byte
}

// 模拟日志或序列化接口（接收 any），故意禁止内联以观察接口装箱逃逸。
//go:noinline
func sink(v any) int {
	return len(fmt.Sprint(v))
}

// 对照 1：大小在编译期固定，且仅在函数内读写，完全留在栈上。
//go:noinline
func onStack(id int) int {
	var item logItem
	item.ID = id
	item.Body[0] = byte(id)
	return int(item.Body[0])
}

// 对照 2：虽然没有把 buf 返回，但长度 n 是运行期变量，
// 编译器无法在编译期为它预留固定栈空间，超阈值后会走堆分配。
//go:noinline
func escapeBySize(n int) int {
	buf := make([]byte, n) 
	buf[0] = 1
	return int(buf[0])
}

// 对照 3：结构体本身不大也没返回，但塞进 any 接口触发装箱逃逸。
//go:noinline
func escapeByAny(id int) int {
	item := logItem{ID: id}
	return sink(item) 
}

func main() {
	var sum int
	for i := range 20_000 {
		sum += onStack(i)
		sum += escapeBySize(256)
		sum += escapeByAny(i)
	}
	// 省略写出 /tmp/escape-allocs.pb.gz 的收尾代码
}examples/go/memory/escape-pprof/main.go

分别用 -gcflags="-m=2" 查看编译期逃逸报告，再运行程序用 pprof 看实际发生的堆分配：

cd examples/go

# 2. 实际运行并采集 heap profile，再按函数行查看累计堆分配
/tmp/escape-pprof
go tool pprof -alloc_space -list="main\." /tmp/escape-allocs.pb.gz终端命令

对照这两份输出可以看出三个常见现象：onStack 全程留在栈上，在 pprof 里没有任何堆分配记录；escapeByAny 仅仅因为把结构体传给了 any 参数，自身装箱就占了 1.50MB，加上下游 fmt.Sprint 一共占总分配的 81.23%；而 escapeBySize(256) 虽然编译器显示 does not escape（切片确实没往外传），但长度 n 在编译期未知且超过栈上小切片内联阈值，运行期在 pprof 里依然抓到了 512.12kB 堆分配。排查性能问题时，不能只看 -gcflags="-m" 的字面结论，需要和 pprof 结合验证。

除此之外，被 go func() 或闭包捕获的局部变量，以及传给底层实现未知的接口方法（例如 io.Writer.Write(buf)，编译器无法判断实现类是否会长期持有 buf），也都会导致堆逃逸。

三层内存分配器

一旦对象落到堆上，运行时就必须快速找到一块空闲内存。高并发服务里每个核每秒可能分配数万个几十字节的小对象，如果每次都向操作系统调 mmap，进内核太慢；如果预先从系统批发一大块内存再用一把全局锁往外切，多核并行时又会像早期调度器那样全部卡在锁竞争上。

Go 采用的是按固定规格预分箱加三层批零的结构：

堆对象分配请求
  ├─ < 16 B 无指针 ──→ Tiny 分配器（拼进同一块 16 B 空间）
  ├─ ≤ 32 KiB     ──→ P.mcache（无锁）
  │                      └─ 不够 → mcentral（按规格分锁）
  │                                  └─ 不够 → mheap（全局页堆）
  └─ > 32 KiB     ──→ 直接找 mheap 分配整页（跳过 mcache/mcentral）三层内存分配路径

在 Go 1.25.8 的 sizeclasses.go 中，小对象被预先划分为 67 种非零规格（NumSizeClasses = 68，从 8B 一直到 MaxSmallSize = 32768 即 32 KiB）。一个 20 字节的对象向上对齐进 24B 规格的 mspan 内存块，用少量内部零头换取极低的外部碎片和快速匹配。

分配路径按局部性分成三层：

  1. mcache（挂在每个 P 上）：在 GMP 调度器 里每个 P 都带有一份专属的 mcache。同一时刻只有一个 M 能持有这张 P，所以当前 M 分配小对象时直接从 P.mcache 取用，完全不用加锁；后续清扫出来的空闲槽位也留在这里原地复用。
  2. mcentral（按规格分类的共享中转站）：某个 P 手上 24B 规格的槽位用完后，向全局 mcentral 批发一整块 mspan。由于 67 种规格各有独立的锁，一个 P 领 24B、另一个 P 领 128B 时互不干扰。
  3. mheap（全局页堆）：mcentral 也没有可用 mspan 时，才加全局锁找 mheap 领新的连续内存页；总库不足时再由 mheap 向操作系统批量申请，长时间闲置的连续页也由它负责归还系统。
对象体积（malloc.go）分配路径设计目的
< 16 B 且不含指针Tiny 分配器把多个小整数或短字符串头拼进同一块 16 B 空间
≤ 32 KiBP.mcache → mcentral → mheap高频小对象本地无锁拿取，清扫后槽位直接复用
> 32 KiB直接找 mheap防止单个大 buffer 占满 P 的本地小缓存

为什么选三色标记，而不是引用计数

内存发出去之后，如何判断哪些对象已经不再使用？

最直观的思路是引用计数：每个堆对象维护一个计数，多一个指针指向就加一，减少就减一，归零立即回收。但这在 Go 里有两个硬伤：一是循环引用（a.next = b; b.next = a）在外部断掉后计数仍为 1，永远无法归零；二是在高并发下，连最普通的 p = q 指针赋值都必须对新旧目标做原子加减，业务代码整体吞吐会明显下降。

因此 Go 选择了追踪式标记-清扫（Mark-Sweep）：平时赋值尽量少做额外操作，等到需要回收时，从所有肯定仍可达的起点（各 goroutine 当前栈和全局变量，统称 GC Roots）顺着指针往下遍历，没摸到的对象统一清理。遍历过程中对象按进度分成三种颜色：

  • 白色：尚未被 GC 访问过。一轮标记结束时依然是白色的对象就是垃圾。
  • 灰色：自己已经被访问到，但它内部持有的指针还没检查完，相当于待办清单。
  • 黑色：自己和所有直接引用的指针都已经检查完成，GC 本轮不会再回头扫它。

并发标记下的漏标问题

如果标记期间停掉所有业务 goroutine（STW），顺着灰色队列扫完绝不会出错；但在几个 GB 的堆上全停扫描会导致停顿过长。一旦允许业务协程和 GC 并发运行，同时发生以下两步就会把还在用的对象误删：

初始状态：A(黑，已扫完)    B(灰，待扫) ──→ C(白，未摸到)

业务并发执行两步：
  1. A.next = C     // 已扫完的 A 新连上 C，GC 不会回头查 A
  2. B.next = nil   // 待扫的 B 断开了通往 C 的旧路

结果：GC 轮到扫 B 时只看到 nil，本轮结束 C 仍是白色，被误删。并发标记漏标过程

混合写屏障：为什么不用给栈加屏障也不用重扫栈

为了堵住并发漏标，需要让编译器在修改指针时插一段钩子代码记录变动，这就是写屏障（Write Barrier）。但 goroutine 栈上的局部变量赋值过于频繁，加写屏障会严重拖慢函数调用，所以 Go 规定写屏障只加在堆对象的指针写入上，栈上不加写屏障。

Go 1.8 引入的混合写屏障（Hybrid Write Barrier），目的就是在不给栈加写屏障的前提下，也省掉标记结束前“再次 STW 重扫所有栈”的昂贵步骤。

先看简化的三色规矩

如果把栈扫描想象成开局一步到位，整套逻辑很容易理解：假设 GC 开始时先把各协程栈上的根扫完标黑（期间栈上新生成对象也直接算黑），之后栈不再重扫；在堆上改指针时，被覆盖踢掉的旧目标涂灰，新写进去的目标也涂灰。既然栈和堆之间无论怎么倒腾指针都逃不过这两条涂灰，自然不会漏标。

对照 Go 1.25.8 源码的实现细节

真实运行时不想在开局一次暂停去扫完几万条协程的栈，而是让各条栈并发逐个扫描。因此 mbarrier.go 里的实际混合写屏障只在新指针涂灰前多加了一个开关：

// 堆上每次执行 *slot = ptr 时由编译器插入的混合写屏障（伪代码）
func writePointer(slot *unsafe.Pointer, ptr unsafe.Pointer) {
	// 1. 删除屏障：改写前先把旧目标涂灰，防“对象从堆挪进黑栈后旧路被断”
	shade(*slot) 
	// 2. 插入屏障：仅当当前协程的栈还没扫完（仍是灰栈）时，顺手保住新目标
	if currentStackIsGrey() {
		shade(ptr) 
	}
	// 3. 真正完成指针写入
	*slot = ptr
}runtime/mbarrier.go

这两句正好对应在“栈无写屏障”的前提下仅有的两种漏标路径：

情况 1（堆 → 黑栈）：s = B.next; B.next = nil
  └─ 改写堆 B.next 时触发 shade(*slot)，先保住旧目标 C

情况 2（灰栈 → 黑堆）：A.next = s; s = nil
  └─ 改写堆 A.next 时因当前栈未扫完触发 shade(ptr)，先保住新目标 C混合写屏障两条防线

一旦当前 goroutine 自己的栈扫描完毕，上面所有指针都已指向灰或黑对象，栈里不再存在未标记的白色对象，第二句判断随之失效，之后全靠第一句删除屏障即可保底。至于并发标记半路上 new 出来的新堆对象（例如 u := &User{} 直接放在已扫描的栈变量上），gcmarknewobject 规定只要处在标记阶段，新分配的堆对象一律直接标黑；哪怕只活了两行就不再使用，也留到下一轮再清理。

为了不让写屏障拖慢每次堆指针赋值，触发时并不会当场执行完整的标记入队逻辑，而是通过汇编快速把指针放进每个 P 自带的 wbBuf 缓冲区（mwbbuf.go），凑够 512 个再批量冲刷到 GC 工作队列。

一轮完整的 GC 周期（与 GMP 联动）

把这些模块装回 mgc.go，一轮 Go GC 一共经过 4 个阶段，包含 2 次极短的 STW。下面是运行 /tmp/escape-pprof 时加上 GODEBUG=gctrace=1 抓到的一行真实日志（为便于阅读按字段分行注释）：

gc 4 @0.084s 0%:
  0.016+0.083+0.006 ms clock   # STW1(0.016) + 并发标记(0.083) + STW2(0.006)
  0.16+0.014/0.037/0+0.067 ms cpu
  3->4->1 MB, 4 MB goal        # 启动3MB → 标完4MB → 存活1MB，本轮目标4MB
  0 MB stacks, 0 MB globals, 10 PGODEBUG=gctrace=1

对应四个阶段的动作是：

  1. 标记准备（第 1 次 STW，0.016 ms，gcStart）：完成上一轮残余清扫，清空 sync.Pool（clearpools，避免池中对象长期保活）；短暂全局暂停（即调度器 findRunnable 开头检查的 sched.gcwaiting），把阶段切换至 _GCmark 并开启写屏障后立刻恢复运行。这一次 STW 是为了确保所有 P 都能看到写屏障已经生效。
  2. 并发标记（不 STW，耗时 0.083 ms）：业务 goroutine 正常推进，同时 gcBgMarkStartWorkers 准备好的后台 GC worker（对应 findRunnable 里 gcBlackenEnabled != 0 时领出的任务）并发扫描栈、全局变量与堆图。如果业务分配内存的速度超过了后台标记速度，运行时会拦住正在狂分配的业务 goroutine，要求它顺手执行一部分**辅助标记（Mutator Assist）**后再继续拿内存，把背压直接加回分配者身上。
  3. 标记终止（第 2 次 STW，0.006 ms，gcMarkDone → gcMarkTermination）：本地和全局标记队列均为空后，先通过 forEachP 冲刷一遍每个 P 的 wbBuf 和 gcw，确认没有新灰对象后进第 2 次 STW 复查一遍 wbBuf，把阶段切回 _GCoff 关闭写屏障，然后恢复世界。因为省掉了重扫全部栈，这一步停顿通常在微秒到几十微秒级别。
  4. 并发清扫与内存归还（不 STW，gcSweep）：标记完还是白色的对象即视为垃圾。后台常驻的 bgsweep 协程逐步清扫，同时业务向 mheap 领新内存页时也会按比例顺手扫掉部分旧页；清出的空闲槽位优先留在 mcache 和 mcentral 复用，长时间闲置不用的连续页再由后台 bgscavenge 归还给操作系统。

对照看上面那行 gctrace 输出：业务真正被全停卡住的时间只有 0.016 + 0.006 = 0.022 ms；堆从 3MB 涨到 4MB 是因为标记期间业务持续新分配了黑对象，真正标出的存活堆只有 1MB，本轮设定的上限目标是 4MB。

触发时机与容器内存控制：GOGC 与 GOMEMLIMIT

GOGC：按存活堆比例算上限（默认 100）

GOGC 本质上是个百分比，决定允许堆在上一轮存活堆的基础上再增长多少，对应 mgcpacer.go：

// GOGC=off 时 gcPercent 为 -1，目标保持最大 uint64（关闭百分比触发）
gcPercentHeapGoal := ^uint64(0)
if gcPercent := c.gcPercent.Load(); gcPercent >= 0 {
	// 基数包含上轮存活堆，以及栈和全局变量的扫描体积，按 GOGC 百分比放大
	scanBase := c.heapMarked + c.lastStackScan.Load() + c.globalsScan.Load()
	gcPercentHeapGoal = c.heapMarked + scanBase*uint64(gcPercent)/100
}
// 堆极小时套用最小保底阈值，避免几 KB 就频繁触发 GC
if gcPercentHeapGoal < c.heapMinimum {
	gcPercentHeapGoal = c.heapMinimum
}runtime/mgcpacer.go:1236-1245

假设上一轮标完存活堆 c.heapMarked 是 1400MB（先忽略占比较小的栈与全局变量扫描量），默认 GOGC=100 会把目标定在约 2800MB，而 GOGC=50 则定在约 2100MB。需要注意，算出来的 goal 是这轮 GC 应该完成回收的上限目标，而不是等到 2100MB 才刚起步；trigger 会根据历史分配和标记速率估算一条跑道 runway，提前在 trigger = goal - runway 处点火开启并发标记。调大 GOGC（例如 200）是用更大的内存空间换取更少的 GC 次数和更低 CPU 开销，调小则相反。

GOMEMLIMIT：容器场景的动态软上限

虽然 Go 1.25 会自动读取容器 CPU 限额来设 GOMAXPROCS，但它不会自动读取容器内存上限来设置 GOMEMLIMIT。不手动配置时，SetMemoryLimit 默认值为 math.MaxInt64（相当于关闭）。

如果一个 K8s 容器内存硬上限是 2GiB，服务长期缓存占了 1.2GiB，按默认 GOGC=100 运行时打算等堆涨到约 2.4GiB 才收完下一轮，还没撞上 GC 目标就会先被内核 OOMKilled。通过环境变量配置 GOMEMLIMIT=1800MiB（或代码中调用 debug.SetMemoryLimit）后，heapGoalInternal 每轮都会取两者中更紧的那个：

// 先取按 GOGC 百分比算出的目标
goal = c.gcPercentHeapGoal.Load()
// 再用 GOMEMLIMIT 扣掉非堆内存与余量反推上限；谁更小听谁的
if newGoal := c.memoryLimitHeapGoal(); newGoal < goal { 
	goal = newGoal
}runtime/mgcpacer.go:943-950

平时内存宽裕（比如存活才 100MB）时，离 1800MiB 还远，系统仍按 GOGC=100 跑，不白费 CPU；一旦缓存涨到 1400MB 逼近红线，memoryLimitHeapGoal() 会动态压低目标，提前频繁触发 GC 并更积极地向系统归还空闲页。

同时要记住 GOMEMLIMIT 是软限制：如果业务确实长期死锁着 1.85GiB 存活对象释放不掉，Go 不会为了死守 1800MiB 而无限死循环 GC 把 CPU 拖死（内部设有 CPU 占用上限保护），代价是接口延迟和 GC CPU 明显升高；一旦总内存最终撑爆容器的 2GiB 硬限，容器照样会被 OOM 杀掉。

排查与对照

遇到内存或 GC 相关的线上告警时，可以先区分最常见的两类表现：

现象常见原因排查方式

在 macOS 上如果本机未安装 graphviz，打开 go tool pprof -http=:8080 后，Graph 调用图会提示缺少 dot，但火焰图（Flame Graph）、Top 和源码行视图（Source）都不受影响，足以直接定位到具体分配语句。

从代码里的逃逸判断到 mcache/mcentral/mheap 的分层分配，再到三色标记、混合写屏障与 GOGC/GOMEMLIMIT 调步，整套内存管理围绕同一件事运转：尽可能把对象留在栈上，进堆后用本地无锁缓存快速复用，并发标记阶段用极短的 STW 换取低停顿，并由百分比与内存软上限共同控制回收节奏。
